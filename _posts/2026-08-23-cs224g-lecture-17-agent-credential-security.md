## 1. 신뢰의 아키텍처 — Ephemeral Token

### 문제

클라이언트(브라우저, 모바일 앱, 데스크톱 에이전트)가 외부 AI API에 **직접** 연결해야 하는 상황이 있습니다. 실시간 오디오처럼 지연시간이 중요하거나, 서버를 거치면 대역폭 비용이 커지는 경우입니다.

그런데 직접 연결하려면 API 키가 필요하고, **클라이언트 코드에 들어간 키는 공개된 것과 같습니다.**

### 패턴 — 4단계

```
1. Frontend  ──── 세션 시작 권한 요청 ────▶  Backend

2.                                        Backend ──── 마스터 API 키로
                                                       단기 토큰 요청 (REST) ────▶ OpenAI

3. Frontend  ◀──── Ephemeral Token 전달 ──── Backend

4. Frontend  ──── Ephemeral Token으로 직접 연결 (WebRTC) ────▶ OpenAI
```

| 단계 | 내용 |
| --- | --- |
| 1 | 프론트엔드가 백엔드에 **세션 시작 권한**을 요청 |
| 2 | 백엔드가 **마스터 API 키**로 제공자에게 **단기(ephemeral) 토큰**을 요청 |
| 3 | 백엔드가 프론트엔드에 **단기 토큰만** 전달 |
| 4 | 프론트엔드가 그 토큰으로 제공자에 **직접 연결** |

> **마스터 API 키를 클라이언트 코드에 절대 노출하지 마십시오.**

### 왜 이게 작동하는가

| 속성 | 내용 |
| --- | --- |
| **수명이 짧다** | 토큰이 유출돼도 곧 만료됨 |
| **범위가 좁다** | 한 세션에만 유효. 계정 전체 권한이 아님 |
| **발급 시점에 정책을 박을 수 있다** | 아래 참조 |
| **취소·감사가 가능하다** | 백엔드가 발급 기록을 갖고 있음 |

**노트 — 세 번째가 이 패턴의 진짜 가치입니다**

단순히 "키를 숨긴다"가 전부가 아닙니다. **토큰을 만드는 순간이 정책을 강제할 수 있는 유일한 지점**입니다.

이 강의의 예시에서는 토큰을 만들 때 세션 설정 자체를 백엔드가 정합니다 — **지시문(persona), 음성, 사용 가능한 도구 목록**까지 전부. 그리고 **클라이언트는 `session.update`를 보내지 않습니다.**

즉 클라이언트가 시스템 프롬프트를 바꾸거나 도구를 추가할 방법이 원천적으로 없습니다. Lecture 5-6의 "보안 가드레일은 사용자가 편집할 수 없는 계층(제품 프롬프트)에 두라"를 **네트워크 경계로 강제한 형태**입니다.

Lecture 5-6에서 지적했듯 프롬프트 계층 분리는 "강한 관례이지 강제된 경계가 아닙니다". 그런데 이 패턴에서는 클라이언트가 애초에 그 필드를 보낼 수 없으므로 **진짜 경계가 됩니다.**

### 일반화

이 패턴은 음성 AI에만 해당하지 않습니다. 다음 상황 전부에 적용됩니다.

- 브라우저에서 LLM API로 직접 스트리밍할 때
- 데스크톱 에이전트가 클라우드 서비스에 붙을 때
- 서드파티 통합에 제한된 권한만 넘길 때
- 사용자 기기에서 실행되는 코드가 회사 자원에 접근할 때

**대응하는 표준 개념:** OAuth 2.0의 단기 액세스 토큰, AWS STS의 임시 자격증명, GCP의 단기 서비스 계정 토큰. 같은 아이디어가 이름만 다르게 존재합니다.

## 2. Sideband 패턴 — 도구 실행을 서버에 두기

### 개념

> 서버가 **같은 세션에 두 번째 연결**을 열어, 모든 이벤트를 보고 도구를 실행하고 대화를 통제하는 패턴.

```
Browser ──── WebRTC (오디오) ────▶ 제공자
                                      ▲
Backend ──── WebSocket (제어) ─────────┘
             같은 세션 ID로 접속
```

| 요소 | 내용 |
| --- | --- |
| **같은 세션, 두 개의 연결** | 브라우저는 오디오용 연결을 유지. 백엔드는 세션 식별자로 두 번째 연결을 염 |
| **서버에서 도구 실행** | 모델이 도구 호출을 내보내면 **백엔드가 받아서** 검증하고, DB나 API를 호출하고, 결과를 돌려줌 |
| **클라이언트는 결과만 받음** | 프론트엔드는 단순한 결과 하나만 받음 |
| **대화 통제** | sideband로 지시를 주입하거나, 도구를 갱신하거나, 응답을 취소할 수 있음 |

> 데이터 조회(재고 확인, DB에서 코드 검증 등)를 **클라이언트에 로직을 노출하지 않고** 수행할 수 있습니다.

**노트 — 이것이 왜 보안 패턴인가**

도구 실행을 클라이언트에서 하면 두 가지가 새어 나갑니다.

1. **검증 로직** — "어떤 조건이면 통과인지"가 클라이언트 코드에 있으면 우회할 수 있습니다
2. **데이터 접근 권한** — 클라이언트가 DB를 조회할 수 있어야 하므로 그 자격증명도 클라이언트에 있어야 합니다

sideband로 옮기면 둘 다 서버에 남습니다. 클라이언트는 "열림/닫힘" 같은 최종 결과만 봅니다.

Lecture 7의 **"LLM은 코드를 실행하지 않는다. 의도를 나타내는 토큰을 내보낼 뿐이고, 실제 작업은 런타임이 한다"**가 여기서 **"그 런타임을 어디에 둘 것인가"**라는 배치 문제로 이어집니다. 답은 **신뢰할 수 있는 쪽**입니다.

## 3. 관련 내용 — 다른 강의와의 연결

이 두 패턴은 코스의 다른 보안 논의와 하나의 그림을 이룹니다.

| 강의 | 내용 | 이 노트와의 관계 |
| --- | --- | --- |
| **L7** 안전 원칙 4·5 | 샌드박싱, 되돌릴 수 없는 작업에 사람 승인 | 실행 권한을 제한하는 원칙 |
| **L9** secret-agent | 비밀이 **프롬프트 컨텍스트와 트레이스 로그**에 들어가지 않게 | 토큰을 얻은 **뒤**의 관리 |
| **L5-6** 지시 3계층 | 보안 가드레일은 사용자가 못 건드리는 계층에 | Ephemeral token이 이를 **네트워크로 강제** |
| **L18** 폭발 반경 | **자격증명을 가진 에이전트 = 거대한 폭발 반경** | 왜 이 모든 게 필요한지의 이유 |

**정리하면 세 겹입니다.**

```
1) 발급   — 단기·좁은 범위 토큰만 클라이언트로  (이 노트)
2) 보관   — 컨텍스트와 로그에 비밀을 남기지 않음  (L9)
3) 실행   — 위험한 작업은 서버에서, 되돌릴 수 없으면 사람 승인  (이 노트 + L7)
```

## 핵심 요약

| 주제 | 결론 |
| --- | --- |
| 원칙 | **마스터 API 키를 클라이언트에 절대 노출하지 마라** |
| Ephemeral Token | 백엔드가 마스터 키로 **단기·좁은 범위 토큰**을 발급해 전달 |
| 진짜 가치 | **발급 시점이 정책을 강제할 수 있는 유일한 지점** — 지시문·도구 목록까지 서버가 고정 |
| Sideband | 도구 실행과 데이터 조회를 **서버 연결에서** 수행. 검증 로직과 DB 권한이 클라이언트로 안 샘 |
| 세 겹 방어 | **발급(단기 토큰) → 보관(로그·컨텍스트 격리) → 실행(서버 측 + 사람 승인)** |
| 대응 표준 | OAuth 2.0 단기 토큰 · AWS STS · GCP 단기 서비스 계정 토큰 |
