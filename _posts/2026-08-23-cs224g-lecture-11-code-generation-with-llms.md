> 이제는 **프로덕션 준비가 된 카테고리이며 빠르게 성숙 중**입니다.

**노트 — 이 연표에서 읽어야 할 변화**

주목할 점은 초점의 이동입니다.

```
코드를 이해하기(요약·검색)  →  코드를 쓰기(자동완성)
        →  작업을 끝내기(에이전트)
```

2016~2019년 연구는 "코드를 이해시키는 것"이 목표였습니다. Copilot 시대는 "다음 줄을 쓰는 것"이었습니다. 지금은 **"이슈를 받아 PR을 내는 것"**입니다. 단위가 줄(line)에서 작업(task)으로 올라갔고, 그래서 검증도 문법 수준이 아니라 **작업 완수 수준**에서 이루어져야 합니다.

#### 1.3 포화(Saturation)

> 이 벤치마크는 이제 거의 완전히 **포화**되었습니다 — Claude Opus 4.6이나 GPT-5.3-Codex 같은 강력한 LLM에게는 사소합니다.
>
> 벤치마크는 점점 빠른 속도로 포화되고 있으며, **새롭고 흥미로운 벤치마크를 만드는 것 자체가 진짜 연구 문제**입니다.

**노트 — pass@k와 "포화"의 의미 (슬라이드에 없는 배경)**

**pass@k**는 코드 생성의 표준 지표입니다. 모델에게 답을 k개 생성시켜서 **그중 하나라도 모든 테스트를 통과하면 성공**으로 칩니다.

- `pass@1` — 한 번에 맞히는 능력 (실사용에 가까움)
- `pass@10`, `pass@100` — 여러 번 시도했을 때. **검증기가 있으면 이 값이 실질 성능이 됩니다**

두 번째 항목이 중요합니다. 컴파일러나 테스트가 있으면 틀린 답을 걸러낼 수 있으므로, 시스템의 실제 성능은 `pass@1`이 아니라 `pass@k`에 가까워집니다. **Lecture 7의 Evaluator-Optimizer가 성능을 크게 올리는 이유가 이 지표로 설명됩니다.**

**"포화"**란 상위 모델들이 모두 95%+를 기록해 서로 구분이 안 되는 상태입니다. 그러면 그 벤치마크는 더 이상 정보를 주지 못합니다.

#### 1.4 새로운 벤치마크 (강의 시점 수치)

| 벤치마크 | 측정 대상 | GPT-5.3-Codex | Opus 4.6 |
| --- | --- | --- | --- |
| **SWE-Bench Pro** | 다중 언어 실제 GitHub 이슈. (Python 전용이던) SWE-Bench Verified를 대체 | 80.0% | **80.8%** |
| **Terminal-Bench 2.0** | 터미널·CLI 코딩 능력. 실제 터미널 워크플로 역량 | **77.2%** | 65.4% |
| **OSWorld-Verified** | 실제 컴퓨터에서의 멀티모달 작업. GUI 조작, 파일 관리, 앱 사용 | 64.7% | **72.7%** |

> SWE-Bench Verified가 2025년의 골드 스탠다드였고, 지금은 **SWE-Bench Pro(다중 언어, 오염 저항성)로 이동** 중입니다.

강의가 던진 질문: **왜 공개되지 않은(held-out) 벤치마크가 가치 있는가?**

**노트 — 답: 오염(contamination)**

벤치마크가 공개되면 그 문제와 정답이 인터넷에 퍼지고, 다음 세대 모델의 **학습 데이터에 들어갑니다.** 그러면 모델은 문제를 푸는 것이 아니라 **기억한 답을 꺼내는 것**이 되고 점수는 실력을 반영하지 못합니다.

이것이 SWE-Bench Pro가 "contamination-resistant"를 내세우는 이유이고, 비공개 held-out 세트가 필요한 이유입니다. **실무에도 그대로 적용됩니다** — 내부 평가 골든셋을 만들 때, 그 데이터가 프롬프트 예시나 문서에 흘러 들어가면 평가가 무의미해집니다.

**노트 — Arena 방식이 뜨는 이유**

Arena는 **사람이 두 출력을 나란히 놓고 어느 쪽이 나은지 고르는** 방식(pairwise comparison, Elo 레이팅)입니다.

장점은 **포화되지 않는다**는 것입니다. 고정된 정답이 없으므로 모델이 아무리 좋아져도 상대 비교는 계속 유효합니다. 또 오염 문제도 약합니다.

단점은 주관성과 비용, 그리고 "사람이 좋아하는 답"과 "정확한 답"이 다를 수 있다는 점입니다. 참고로 이 비교 판단 방식은 Lecture 3에서 본 RLHF의 보상 모델 학습과 같은 원리입니다.

### 7. 추론 방법의 계보

#### 7.1 Chain-of-Thought (CoT)

- LLM이 입력에서 출력까지 **추론 단계를 순차적으로 생성**하도록 유도
- 최초 소개: *PaLM: Scaling Language Modeling with Pathways* (Chowdhery, Catasta et al., 2022)
- **한계:** 체인이 길어질수록 **오류가 전파**됨

```
Input → S1 → S2 → S3 → Output   (선형)
```

#### 7.2 Tree-of-Thoughts (ToT)

- CoT를 확장해 **BFS·DFS 같은 탐색 알고리즘으로 여러 추론 경로를 탐색** (Yao et al., 2023.05)
- **한계:** 오직 LLM의 **내부 지식에만** 의존

```
Input → S1 ─┬─ S2 ─┬─ S3
            ├─ S2 ─┼─ S3   (분기 탐색)
            └─ S2 ─┴─ S3
```

#### 7.3 Reasoning via Planning (RAP)

- **몬테카를로 트리 탐색(MCTS)**으로 추론 연쇄를 계획 (Hao et al., 2023.10)
- **한계:** 역시 **외부 피드백이 없음**

**노트 — 세 방법의 공통 한계가 다음 절로 이어집니다**

CoT·ToT·RAP는 전부 **모델 머릿속에서만** 일어납니다. 아무리 정교하게 탐색해도 그 평가가 모델 자신의 판단이라면, 모델이 틀리게 확신하는 지점은 걸러지지 않습니다. 여기서 **외부 피드백을 도입하는 것**이 다음 계보입니다.

---

### 8. 의사결정 방법의 계보

#### 8.1 ReAct

- **행동(action)과 관측(observation)을 번갈아** 하도록 프롬프팅 (Yao et al., 2023.03)
- **한계:** **하나의 경로를 탐욕적으로** 따라가며 적응하지 못함

```
Input → S1 → S2 → S3 → Output
         ↑     ↑     ↑
      Observation (외부 피드백!)
```

#### 8.2 Reflexion

- ReAct에 **자기성찰(self-reflection)**을 추가 (Shinn et al., 2023.10)
- CoT와 유사하게, **문제를 더 오래 생각할 시간**을 줌으로써 성능 향상
- **한계:** 각 단계에서 **대안을 고려하지 않음**

```
Input → S1 → S2 → S3 → Output
         ↑     ↑     ↑
      Observation + Reflection
```

**노트 — Reflexion이 ReAct와 정확히 무엇이 다른가**

ReAct의 루프는 `Thought → Action → Observation` 반복입니다. 실패하면 **다음 행동을 다르게** 시도할 뿐, 왜 실패했는지 명시적으로 정리하지 않습니다.

Reflexion은 시도가 끝난 뒤 **"무엇이 잘못됐는지"를 언어로 요약해 메모리에 남깁니다.** 다음 시도에서 그 반성문이 컨텍스트에 들어가므로 같은 실수를 반복하지 않습니다.

즉 **실패를 재사용 가능한 텍스트 자산으로 바꾸는 것**이 Reflexion의 기여입니다. 실무에서 "컴파일 오류를 다음 프롬프트에 붙인다"가 바로 이 아이디어의 가장 단순한 형태입니다.

#### 8.3 LATS (Language Agent Tree Search) ⭐

- **추론 방법과 의사결정 방법의 강점을 원리적 탐색으로 통합** (Zhou et al., 2023.12)
- **환경 피드백과 자기성찰**로 양쪽의 한계를 극복

```
Input → 트리 탐색(여러 S1/S2/S3 분기)
          ↑        ↑
     Observation  Reflection
```

#### 8.4 LATS의 6단계

| 단계 | 하는 일 |
| --- | --- |
| 1. **Selection** | 점수를 기준으로 이동할 노드를 선택 |
| 2. **Expansion** | 선택된 노드에서 정책 pθ로부터 **n개의 행동을 샘플링**해 트리를 확장 |
| 3. **Evaluation** | 각 자식 노드에 **스칼라 값을 할당**. 과제 완수 진척도를 정량화해 유망한 가지로 유도 |
| 4. **Simulation** | 선택된 노드를 **종료 상태에 도달할 때까지** 확장. 각 깊이에서 샘플·평가하되 **가장 값이 높은 노드를 우선** |
| 5. **Backpropagation** | 궤적의 결과를 바탕으로 **트리의 값들을 갱신** |
| 6. **Reflection** | 실패한 종료 노드를 만나면, 궤적과 최종 보상을 주고 **오류를 요약하고 더 나은 대안을 제안하는 언어적 자기성찰**을 생성 |

**노트 — MCTS를 알면 LATS가 바로 이해됩니다**

1~5단계는 **몬테카를로 트리 탐색(MCTS)** 그대로입니다. AlphaGo가 쓴 그 알고리즘입니다.

| MCTS 단계 | 바둑에서 | LATS에서 |
| --- | --- | --- |
| Selection | 유망한 수를 따라 내려감 | 유망한 추론 경로를 따라감 |
| Expansion | 새 수를 놓아 봄 | LLM이 다음 행동 n개를 제안 |
| Simulation | 끝까지 두어 봄 | 종료까지 실행해 봄 |
| Backpropagation | 승패를 위로 전파 | 보상을 위로 전파 |

LATS의 독창성은 **6단계 Reflection**입니다. MCTS는 숫자(승률)만 역전파하지만, LATS는 **언어로 된 반성문**도 남깁니다. 숫자는 "이 경로가 나빴다"만 말하지만 반성문은 **"왜 나빴는지"**를 말합니다.

이것이 GPT-3.5+LATS가 GPT-4를 이긴 메커니즘입니다 — **탐색 + 외부 피드백 + 언어적 학습**을 추론 시점에 얹은 것입니다.

### 9. 토큰 공간에서의 RL 기반 추론

- OpenAI의 o-시리즈(o1~o4)가 **토큰 공간에서의 RL 기반 추론**을 개척
- 널리 채택됨: Claude의 extended thinking, DeepSeek R1, Gemini의 thinking mode

> 강의가 던진 질문: **에이전트 기법에 대한 "bitter lesson"인가?**
>
> *"RL is all you need"*

**노트 — "Bitter Lesson"이 무슨 말인가**

Rich Sutton의 2019년 에세이 *The Bitter Lesson*을 가리킵니다. 요지는 이렇습니다.

> AI 역사에서 **사람이 손으로 설계한 구조**는 단기적으로 이기지만, 장기적으로는 **계산량을 늘리는 범용적 방법(탐색과 학습)**이 항상 이겨 왔다.

체스에서 사람이 넣은 전략 지식이 무차별 탐색에 졌고, 컴퓨터 비전에서 손으로 만든 특징이 CNN에 졌습니다.

강의의 질문은 이것입니다 — **LATS 같은 정교한 에이전트 스캐폴딩도 결국 "생각을 더 하도록 RL로 학습된 모델"에 밀려나는 것 아닌가?**

실제로 그런 흐름이 있습니다. o-시리즈 이후 CoT를 명시적으로 프롬프팅할 필요가 줄었습니다. 모델이 이미 그걸 합니다.

**다만 이 강의와 Lecture 7이 함께 말하는 반론이 있습니다** — 모델 내부에서 아무리 잘 생각해도 **외부 세계의 피드백(컴파일러, 테스트, DB)은 대체할 수 없습니다.** 스캐폴딩 중에서 "생각을 대신해 주는 부분"은 사라져도, **"현실과 연결해 주는 부분"은 남습니다.** 그래서 실무적 결론은 여전히 검증 루프를 만들라는 쪽입니다.

### 10. 코드 생성을 현명하게 쓰기

> 에이전트는 필요한 지식을 얻는 대단히 강력한 방법을 제공합니다. **추상화 계층을 올라가십시오. 레버리지를 얻으십시오.**
>
> **— 단, 감당할 수 있는 것보다 더 많이는 말고.**

**왜 그런가:**

- **학습이 중요합니다**
- **자기 코드를 이해하는 것이 중요합니다**
- **유지보수와 지식 전수가 중요합니다**
  - 전적으로 에이전트가 작성한 프로젝트는 여전히 **"스파게티 코드"**를 낳는 경향이 있습니다. **작동은 합니다!** 하지만 이해하고 유지보수하기 혼란스럽습니다

**노트 — 이 경고를 진지하게 받아들일 것**

"작동은 한다"가 함정입니다. 테스트가 통과하고 기능이 돌아가면 문제가 없어 보이지만, 6개월 뒤 그 코드를 고쳐야 할 때 비용이 폭발합니다.

실무적 방어선은 두 가지입니다.
1. **에이전트에게 구조를 지시하기** — 아키텍처를 사람이 정하고 구현만 맡김
2. **읽을 수 없는 코드는 머지하지 않기** — 리뷰에서 "이해 못 하겠다"를 정당한 반려 사유로 인정

### 11. 코딩 에이전트 셋업 3단계

| 단계 | 이름 | 내용 |
| --- | --- | --- |
| 1 | **Configure** | `agents.md` / `CLAUDE.md`를 **살아 있는 문서**로 사용. git에 체크인. 자주 갱신. **에이전트에게 갱신을 시킬 것** |
| 2 | **Plan** | **계획 모드로 시작.** 코드를 쓰기 전에 계획을 다듬을 것. **좋은 계획이 원샷 실행을 가능하게 함** |
| 3 | **Verify** | 에이전트에게 **피드백 루프**를 제공: 테스트, 린터, 훅. **검증은 단일 최대의 품질 배수** |

**추가 권고:**

- 반복되는 워크플로에 **커스텀 슬래시 커맨드**
- 설정에서 **권한을 미리 구성**
- Slack, 이슈 트래커, 오류 모니터링에 **연결**

> **검증 피드백 루프 → 출력 품질 2~3배**

**노트 — 3단계의 순서가 곧 우선순위입니다**

강의는 "Verification is the single biggest quality multiplier"라고 못 박습니다. Lecture 7의 Evaluator-Optimizer, Lecture 3의 Lean 증명 사례와 완전히 같은 메시지입니다.

주목할 점은 **2단계(Plan)가 1단계와 3단계 사이에 있다는 것**입니다. 계획을 먼저 다듬으면 "원샷 실행"이 가능해지고, 그러면 검증 루프를 도는 횟수가 줄어 비용이 내려갑니다. 계획은 검증의 대체재가 아니라 **검증 횟수를 줄이는 수단**입니다.

### 12. Vibe Engineering — 코딩 에이전트로 30배 빠르게

| # | 원칙 | 내용 |
| --- | --- | --- |
| 1 | **시작하라** | 이것은 결정적 경쟁 우위다. **검은 휘두르는 사람만큼만 좋다** |
| 2 | **명확성이 전부다** | 프롬프팅 전에 생각하라. 모델이 어떻게 해석할지 알라. 협업적 계획을 쓰라 |
| 3 | **에이전트를 병렬로 돌려라** | 5개 이상 동시에. **중요한 속도 향상.** git worktree를 쓰거나 그냥 트리를 공유시켜라 |
| 4 | **TDD와 그 너머** | TDD → 테스트 하네스 → 일회용 앱. 상태를 흉내 내기 위해 **병렬 DB를 띄워라** |
| 5 | **재시작을 두려워 말라** | 더 나은 기반 = 더 높은 잠재력. **더 나은 컨텍스트로 다시 만드는 게 종종 더 빠르고 낫다** |
| 6 | **소프트웨어를 살아 있는 것으로** | 배포하고 빠르게 적응하라. 작은 버그는 1분 내 수정. **인프라·보안에는 적용하지 말 것** |
| 7 | **모델을 알라** | 강점과 약점에 대한 직관을 쌓아라. **몇 달 전 가이드는 이미 낡았다** |
| 8 | **품질을 지켜라** | **삶아지는 개구리**: 방치하면 AI가 품질을 서서히 떨어뜨린다. 기준을 엄격히 유지하라. `agents.md`가 도움이 된다 |

**노트 — 5번과 8번이 반직관적이지만 중요합니다**

**5번(재시작)** — 사람이 짠 코드는 매몰 비용이 커서 다시 짜기 아깝지만, 에이전트가 짠 코드는 다시 짜는 비용이 거의 0입니다. **"고쳐 쓰기보다 다시 쓰기"의 손익분기점이 완전히 이동했습니다.** 30분 디버깅할 것을 더 나은 프롬프트로 5분 만에 다시 만드는 게 나은 경우가 많습니다.

**8번(삶아지는 개구리)** — 한 번에 큰 품질 저하가 오는 게 아니라 매 커밋마다 조금씩 내려갑니다. 각각은 허용 범위처럼 보입니다. 그래서 **자동화된 기준선**(린터, 복잡도 한계, 커버리지 하한)이 필요합니다 — 사람의 눈은 점진적 하락을 못 잡습니다.

### 13. 프롬프팅 실습 — SudoLang

- **SudoLang**은 LLM을 인터프리터로 삼는 **자연어 제약 기반 의사 프로그래밍 언어**입니다

#### 14.1 포함할 것 / 유지하는 법

| 포함할 것 | 유지하는 법 |
| --- | --- |

> **에이전트가 실수하면 그것을 문서화하라 → 다시 반복하지 않는다.**

#### 14.2 훌륭한 agents.md의 해부 (GitHub 저장소 2,500개+ 분석)

| 항목 | 내용 |
| --- | --- |
| **Commands** | **실행 가능한 명령을 맨 앞에.** `npm test`, `pytest -v`, `bun run typecheck` |
| **Testing** | 테스트 명령, 커버리지 기대치, CI/CD 계획 위치 |
| **Project Structure** | 버전을 포함한 스택, 주요 디렉터리, 파일 위치. "React 18 + TypeScript + Vite" |
| **Code Style** | **설명이 아니라 예시를 보여줄 것.** 좋은 코드 vs 나쁜 코드 스니펫. **예시가 치트키다.** 기존 저장소를 가리켜도 됨 |
| **Git Workflow** | 브랜치 명명, 커밋 형식, PR 관례, 리뷰 기준 |
| **Boundaries** | **3단계: 항상 할 것 / 먼저 물어볼 것 / 절대 하지 말 것** |

> 모호하면 실패합니다.
> ❌ "도움이 되는 코딩 어시스턴트"
> ✅ **"이 예시들을 따르는 React 컴포넌트 테스트 엔지니어"**

#### 14.3 실제 예시 — Anthropic의 claude-code-action

```markdown
# Commands
bun test             # Run tests
bun run typecheck    # TypeScript checks
bun run format       # Format with prettier

# What This Is
A GitHub Action that lets Claude respond
to @claude mentions on issues/PRs...

# Things That Will Bite You
- Strict TypeScript: noUnusedLocals is on
- Discriminated unions for GitHub context
- Token lifecycle: revocation is in always()
- Integration tests are in a separate repo

# Code Conventions
- Runtime is Bun, not Node
- Imports don't need .js extensions
- GitHub API calls use retry logic
```

**무엇이 이것을 훌륭하게 만드는가:**

| 요소 | 이유 |
| --- | --- |
| ✓ 명령이 맨 앞 | 에이전트가 빌드·테스트·포맷 방법을 정확히 안다 |
| ✓ 아키텍처 맥락 | 프로젝트가 무엇이고 조각들이 어떻게 연결되는지 설명 |
| ✓ **함정 문서화** | "Things That Will Bite You"가 반복 실수를 막는다 |
| ✓ 관례 명시 | 런타임, import 스타일, 재시도 패턴 — 모호함 없음 |
| ✓ **간결함** | **약 40줄. 소설이 아니다.** 에이전트에게 필요한 것만 |

**노트 — Boundaries 3단계가 가장 실무적인 부분입니다**

| 단계 | 예시 |
| --- | --- |
| **Always do** | 수정 후 테스트 실행, 기존 코드 스타일 따르기 |
| **Ask first** | 의존성 추가, 스키마 변경, 공개 API 변경 |
| **Never do** | 프로덕션 DB 접근, 시크릿 커밋, force push, 마이그레이션 삭제 |

Lecture 7의 "되돌릴 수 없는 작업에는 사람 승인"을 **문서로 구현한 형태**입니다. 그리고 "약 40줄"이라는 제약이 중요합니다 — 이 문서는 **매 요청마다 컨텍스트에 들어가므로**, 길면 토큰 예산을 먹고 Lost in the Middle의 희생양이 됩니다(Lecture 5-6).

## Part 5: Ephemeral Software & 환경 엔지니어링

### 15. 테스트의 4단계 사다리

> **TDD 다음 단계.** 위로 갈수록 복잡도와 현실성이 증가합니다.

| 단계 | 이름 | 내용 |
| --- | --- | --- |
| 1 | **Unit Tests (TDD)** | 기반 층. **LLM은 구조를 좋아한다.** "테스트를 쓰고, 통과할 때까지 멈추지 마라" — **ML 학습 잡처럼 밤새 돌릴 수 있다** |
| 2 | **AI Tests (LLM-as-Judge)** | 평가자가 LLM인 유닛 테스트. 구조화된 테스트 형식. **AI 앱에는 필수** |
| 3 | **Ephemeral Applications** | **오직 테스트를 위해 만드는 일회용 앱**: 부하 테스트용 봇넷, 입력 놀이터, API 트리거 앱. **완전히 삭제 가능** |
| 4 | **Simulation Environments** | 실제 서비스를 갖춘 완전한 샌드박스 환경. **에이전트가 반대편에서 실제 사용자를 흉내 냄** |

**노트 — 1단계의 "밤새 돌린다"가 새로운 발상입니다**

"테스트가 통과할 때까지 멈추지 마라"를 밤새 돌리는 것은, 사람의 시간과 기계의 시간을 분리하는 발상입니다. 검증기가 확실하면 **에이전트가 몇 백 번 틀려도 상관없습니다** — 비용만 지불하면 됩니다.

이것이 Part 2의 `pass@k` 논의와 정확히 이어집니다. **검증기가 있으면 시도 횟수를 늘려 정확도를 사는 것이 가능**해집니다.

### 16. 환경 엔지니어링 예시

    ┌────────────────┬────────────────┬────────────────┐

### 강의의 논지

```
벤치마크는 계속 포화된다 → 측정 기준이 실세계 영향으로 이동 중
        ↓
그런데 기법이 모델 크기를 이길 수 있다 (LATS)
        ↓
기법의 핵심은 외부 피드백 = 검증
        ↓
그래서 실무에서도 검증이 단일 최대의 품질 배수
        ↓
검증을 위한 환경을 만드는 것이 다음 단계 (Ephemeral / Simulation)
```

### 한 문장으로 압축

| 주제 | 결론 |
| --- | --- |
| 벤치마크 | HumanEval은 포화. 지금은 **SWE-Bench Pro / Terminal-Bench / OSWorld** |
| held-out의 가치 | **오염(contamination)** 방지 — 내부 골든셋에도 그대로 적용 |
| 기법 vs 크기 | **GPT-3.5 + LATS(83.8) > GPT-4(79.3)** |
| 추론 방법 계보 | CoT → ToT → RAP — 전부 **외부 피드백이 없다** |
| 의사결정 계보 | ReAct → Reflexion → LATS — **외부 피드백 + 언어적 반성** |
| Reflexion의 기여 | 실패를 **재사용 가능한 텍스트**로 바꿈 |
| bitter lesson | 스캐폴딩 중 "생각 대행"은 사라져도 **"현실 연결"은 남는다** |
| 에이전트 셋업 | **Configure → Plan → Verify** |
| 최대 레버 | **검증 피드백 루프 = 품질 2~3배** |
| agents.md | 명령을 맨 앞, 예시로 보여주기, 함정 문서화, **40줄 내외** |
| 경계 | **Always / Ask first / Never** 3단계 |
| 테스트 | 단위 → AI 테스트 → 일회용 앱 → 시뮬레이션 환경 |

### 가장 중요한 세 문장

1. **"Verification is the single biggest quality multiplier."**
2. **기법이 모델 크기를 이길 수 있다** — 단, 그 기법의 핵심은 외부 피드백이다.
3. **에이전트가 실수하면 문서화하라 — 다시 반복하지 않는다.**
