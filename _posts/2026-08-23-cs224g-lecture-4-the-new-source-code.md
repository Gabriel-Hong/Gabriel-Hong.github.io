## 강의 개요

슬라이드 53장에 텍스트는 5.3KB뿐입니다. **문장 하나가 슬라이드 하나인 형식**이라 밀도가 매우 높습니다. 프레젠테이션으로는 강렬하고, 노트로 정리하면 격언 모음처럼 됩니다.

핵심 주장은 한 문장입니다.

> **프롬프트는 설정(configuration)이 아니라 실행 가능한 로직(executable logic)이다.**
> 따라서 소스코드에 갖춰준 인프라를 프롬프트에도 갖춰야 한다.

**강의 목차:**

1. 데모는 거짓말이다
2. 프롬프트란 무엇인가
3. 컴퓨팅 과거의 산출물들
4. **AI 개발 라이프사이클** — Iterate / Evaluate / Deploy / Monitor
5. 정리

## Part 1: 데모는 거짓말이다

| 통계 | 내용 |
| --- | --- |
| **87%** | **LLM 기반 프로젝트가 프로덕션에 도달하지 못함** |
| **40%** | **2027년까지 취소될 것 — 부실한 리스크 통제 등의 이유로** |

**노트 — 이 숫자의 의미**

데모는 쉽고 프로덕션은 어렵다는 것이 이 강의 전체의 전제입니다. 그리고 87%가 죽는 지점은 **모델 성능이 아니라 운영 체계**입니다 — 버전 관리가 없고, 회귀를 감지할 수 없고, 왜 어제보다 나빠졌는지 설명할 수 없어서 죽습니다.

Lecture 10의 "LLM은 거의 절대 제약이 아니다"와 같은 진단입니다.

## Part 2: 프롬프트란 무엇인가

### 1. 전통적 소프트웨어와의 차이

| | 입출력 관계 |
| --- | --- |
| **전통적 소프트웨어** | 같은 입력 → **같은 출력** |
| **AI 애플리케이션** | 같은 입력 → **다른 출력** |

> **출력만이 아닙니다. 입력도 바뀌었습니다.**
> 텍스트. 이미지. 오디오. 비디오. 문서.
> 맥락 의존적이고, 대화를 인식합니다.

### 2. 프롬프트가 실제로 인코딩하는 것

- 비즈니스 로직
- 회사의 지식
- 운영 지능(operational intelligence)
- 안전 제약
- 사용자 지시
- … (외 다수)

> **프롬프트는 설정이 아니다. 프롬프트는 실행 가능한 로직이다.**

**노트 — 왜 이 구분이 실무를 바꾸는가**

프롬프트를 "설정값"으로 취급하면 자연스럽게 이렇게 됩니다 — 환경변수나 DB 컬럼에 넣고, 누가 언제 바꿨는지 추적하지 않고, 바꾸기 전에 테스트하지 않고, 문제가 생겨도 롤백할 방법이 없습니다.

"실행 가능한 로직"으로 취급하면 **코드에 하는 모든 것을 해야 합니다** — 리뷰, 버전 관리, 테스트, 스테이징, 롤백, 감사 추적. 다음 파트의 주장이 전부 여기서 나옵니다.

## Part 3: 컴퓨팅 과거의 산출물들

> **모든 컴퓨팅 패러다임은 새로운 산출물(artifact)을 만든다.**

| 시대 | 산출물 | 그에 맞춰 만들어진 인프라 |
| --- | --- | --- |
| **1950s** | 펀치 카드 | 카드 리더, 소터 등 |
| **1970s** | 터미널 명령 | 셸, 컴파일러 등 |
| **1990s** | **소스 코드** | **버전 관리, CI/CD, Pull Request 등** |
| **2020s** | **프롬프트** | **???** |

> **새로운 산출물에는 새로운 인프라가 필요하다.**

### 3. 수십 년에 걸쳐 코드를 위해 만든 것

- 버전 관리
- 테스팅 & CI/CD
- 환경 관리
- 모니터링 & 관측성
- … (외 다수)

> **프롬프트에도 이 모두가 필요하다.**

## Part 4: AI 개발 라이프사이클

```
        Iterate
       ↗       ↘
  Monitor      Evaluate

        Deploy

      연속적 순환
```

---

### 4. Iterate — 추측에서 엔지니어링으로

| ❌ 지금 대부분 | ✓ 되어야 할 것 |
| --- | --- |
| **복사. 붙여넣기. 기도.** | 구조화된 실험 |
| | **diff가 있는 버전 이력** |
| | 나란히 놓고 비교하는 프롬프팅 |
| | 유스케이스 주도 개발 |

**노트 — "Copy. Paste. Pray."**

세 단어로 현재 실무를 정확히 묘사합니다. 프롬프트를 채팅창에서 고치고, 잘 되는 것 같으면 코드에 붙여넣고, 잘 되기를 바랍니다. 이전 버전이 무엇이었는지, 무엇을 바꿨는지, 정말 나아졌는지 아무도 모릅니다.

---

### 5. Evaluate — 감(vibes)에서 지표로

**왜 어려운가:**

- 출력이 매번 다르다
- **사람은 확장되지 않는다**
- 단순한 지표는 뉘앙스를 놓친다
- **"좋음"이 무엇인지 보기 전에는 모른다**

#### 핵심 주장들

> **Evals는 테스트가 아니다. Evals는 피드백 루프다.**

> **목표는 eval을 통과하는 것이 아니다. 목표는 더 빨리 배우고 반복하는 것이다.**

> **Eval을 먼저 작성하라. 데이터를 먼저 보라.**

> 출력을 채점하려면 기준이 필요하다.
> **그런데 출력을 채점해 봐야 기준을 정의할 수 있다.**

> **감과 데이터가 어긋나면, 감을 믿어라.**

**노트 — 마지막 두 개가 흥미롭습니다**

**"닭과 달걀"** — 기준 없이 채점할 수 없고, 채점해 보지 않으면 기준을 못 만듭니다. 해법은 순서가 아니라 반복입니다. 20개를 대충 채점해 보면서 기준이 드러나고, 그 기준으로 다시 채점하고, 다시 다듬습니다. **처음부터 완벽한 루브릭을 설계하려 하면 시작을 못 합니다.**

**"감을 믿어라"** — 반직관적으로 들리지만 맞습니다. 지표가 좋아졌는데 결과물이 나빠 보인다면, **지표가 잘못 설계된 것**입니다. 지표는 목표의 대리물(proxy)일 뿐이고, 대리물이 실제와 어긋나면 고쳐야 할 건 실제가 아니라 대리물입니다.

#### LLM as a Judge

> **항상 이진(binary). 통과 아니면 실패.**

> **1~10 척도를 절대 쓰지 마라. 3.5와 7.2의 차이를 아무도 모른다.**

#### 규모

> **대부분의 애플리케이션에는 eval 47개면 충분하다.**

#### 역할 분담

> **엔지니어는 인프라를 만든다. 도메인 전문가는 루브릭을 쓴다.**

**노트 — 세 가지 다 실무에 바로 적용됩니다**

**이진 판정** — Lecture 5-6의 "점수 매기기를 피하고 이진 판단으로"와 정확히 같은 조언이 다른 강사에게서 독립적으로 나왔습니다. 두 번 나왔다는 것은 신뢰할 만합니다.

**47개** — 어림수지만 유용한 기준점입니다. "수백 개를 만들어야 시작할 수 있다"는 부담을 없애줍니다. Lecture 9가 "트레이스 30~50개"를 말한 것과도 규모가 맞습니다.

**역할 분담** — 루브릭을 엔지니어가 쓰면 안 됩니다. 무엇이 좋은 구조 설계 결과인지는 구조 엔지니어가 압니다. 엔지니어는 그 판단을 자동으로 돌릴 수 있게 만드는 사람입니다.

---

### 6. Deploy — 혼돈에서 통제로

> **프롬프트 변경 빈도 ≠ 코드 변경 빈도**

그럼에도 여전히 필요한 것:

- 버전 관리
- **롤백**
- 감사 추적(audit trail)
- 환경(개발/스테이징/프로덕션)
- … (외 다수)

> 그리고 **엔지니어와 도메인 전문가 둘 다.**

**노트 — 변경 빈도가 다르다는 게 왜 문제인가**

프롬프트는 코드보다 훨씬 자주 바뀝니다. 하루에 열 번 고칠 수도 있습니다. 그런데 코드 배포 파이프라인에 묶어 두면 매번 빌드·테스트·배포를 거쳐야 해서 반복 속도가 죽습니다.

반대로 프롬프트를 DB에 넣고 즉시 반영되게 하면 빠르지만 **통제가 사라집니다.** 이 긴장이 프롬프트 관리 도구가 별도로 존재하는 이유입니다 — 코드와 분리된 배포 경로를 갖되, 버전·롤백·감사는 유지하는 것.

---

### 7. Monitor — 루프를 닫고 플라이휠을 만들라

```
실제 데이터 → 더 나은 프롬프트 → 데이터셋 → Evals
     ↑                                      ↓
     └──────────── 데이터 플라이휠 ───────────┘
```

> **프로덕션 데이터에 대해 eval을 지속적으로 실행하라.**

**노트 — Lecture 15의 플라이휠과 같습니다**

Lecture 15가 제품·데이터 관점에서 말한 플라이휠을, 여기서는 프롬프트 개선 관점에서 말합니다. 그리고 Lecture 15에서 지적한 "가장 흔한 고장 = 데이터→모델 반영 경로 부재"가 여기서는 **"프로덕션 데이터에 eval을 안 돌리는 것"**으로 나타납니다.

로그는 쌓는데 그 로그로 평가를 돌리지 않으면 플라이휠이 아니라 창고입니다.

## Part 5: 오늘 어디서 시작하는가 ⭐

강의가 제시한 5단계입니다.

| # | 단계 |
| --- | --- |
| 1 | **유스케이스 하나를 만든다** |
| 2 | **트레이스 20개를 본다** |
| 3 | **예제 20개짜리 데이터셋을 만든다** |
| 4 | **프롬프트를 반복하고 버전 관리한다** |
| 5 | **기본 모니터링을 붙인다** |

**노트 — 이 5단계가 이 강의에서 가장 실용적인 부분입니다**

Lecture 9의 "트레이스 30~50개 검토", Lecture 7의 "골든 데이터셋 구축"과 규모가 일치합니다. **세 강의가 독립적으로 같은 출발점을 제시합니다 — 20~50건.**

주목할 것은 **2번이 3번보다 먼저**라는 점입니다. 데이터셋을 먼저 설계하는 게 아니라 **실제 트레이스를 먼저 눈으로 보고**, 거기서 무엇을 평가해야 하는지 알아낸 다음 데이터셋을 만듭니다. Part 4의 "닭과 달걀" 문제에 대한 실무적 해답입니다.

## 핵심 요약

### 강의의 논지

```
데모는 쉽고 프로덕션은 어렵다 (87%가 실패)
        ↓
프롬프트는 설정이 아니라 실행 가능한 로직이다
        ↓
모든 패러다임은 새 산출물을 만들고, 새 산출물엔 새 인프라가 필요하다
        ↓
소스코드에 준 것을 프롬프트에도 주어야 한다
   (버전관리 · 테스트 · 환경 · 모니터링)
        ↓
Iterate → Evaluate → Deploy → Monitor 를 계속 돈다
```

### 한 문장으로 압축

| 주제 | 결론 |
| --- | --- |
| 현실 | **LLM 프로젝트의 87%가 프로덕션에 못 간다** |
| 프롬프트의 정체 | **설정이 아니라 실행 가능한 로직** |
| 역사적 위치 | 펀치카드 → 터미널 명령 → 소스코드 → **프롬프트** |
| Iterate | "Copy. Paste. Pray."에서 **diff 있는 버전 이력**으로 |
| Evals의 정체 | **테스트가 아니라 피드백 루프** |
| Eval 목표 | 통과가 아니라 **더 빨리 배우는 것** |
| 순서 | **Eval을 먼저 쓰고, 데이터를 먼저 봐라** |
| 닭과 달걀 | 기준↔채점은 순서가 아니라 **반복**으로 푼다 |
| 감 vs 데이터 | **어긋나면 감을 믿어라** (지표가 잘못 설계된 것) |
| LLM Judge | **항상 이진.** 1~10 척도 금지 |
| 규모 | **47개면 대부분 충분** |
| 역할 | **엔지니어는 인프라, 도메인 전문가는 루브릭** |
| Deploy | 프롬프트 변경 빈도 ≠ 코드 변경 빈도. **롤백과 감사 추적은 필수** |
| Monitor | **프로덕션 데이터에 eval을 계속 돌려라** |
| 시작법 | 유스케이스 1개 → **트레이스 20개** → 예제 20개 → 버전관리 → 모니터링 |

### 가장 중요한 네 문장

1. **"Prompts are not configuration. Prompts are executable logic."**
2. **"Evals are not tests. Evals are feedback loops."**
3. **"LLM as a Judge: always binary. Never use a 1-10 scale."**
4. **"Write evals first. Look at the data first."**
