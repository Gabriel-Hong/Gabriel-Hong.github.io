## 강의 개요

강의의 출발점은 한 문장입니다.

> **Context Engineering supplanting Prompt Engineering**
> (컨텍스트 엔지니어링이 프롬프트 엔지니어링을 대체하고 있다)

프롬프트 문구를 다듬는 것보다, **모델에게 무엇을 보여줄지를 설계하는 것**이 성능을 더 크게 좌우한다는 것이 핵심 주장입니다.

**L6 학습 목표 (슬라이드 명시):**

1. 컨텍스트 엔지니어링을 **질의 표현이 아니라 정보 공급의 아키텍처**로 정의하기
2. 사용자 메시지 외의 전체 스택 열거하기 — 시스템 프롬프트, 대화 이력, 도구 정의, 파라미터
3. 어떤 컨텍스트 요소가 **애플리케이션 개발자의 통제 아래** 있는지 식별하기
4. 정보 풍부함과 토큰 예산 제약의 균형을 잡는 컨텍스트 전략 수립하기

## Part 1: 모델을 어떻게 생각할 것인가 — 세 가지 비유

강의는 모델에 대한 세 가지 사고 모델을 제시합니다. 셋 다 유용하지만 강조점이 다릅니다.

### 1. 비결정론적 CPU

| 항목 | 내용 |
| --- | --- |
| 프롬프트 | 최대 천만 토큰(책 100권) 길이의 **OP 코드** |
| 출력 | 역시 방대함 (책 한 권 분량) |
| 입출력 공간 | 사실상 무한 |
| 그럼에도 | 출력이 우리 경험과 연결된다 |
| 입력을 조절하면 | 출력이 **높은 상관도로** 변한다 |

> **컨텍스트 엔지니어링은 원하는 결과를 신뢰성 있게 복원해 내는 방법이다.**

### 2. 똑똑하지만 경험 없는 인턴

가장 실무적인 비유입니다.

| 특성 | 함의 |
| --- | --- |
| 엄청난 양의 지식 | 아는 건 많음 |
| **무슨 일이 있어도 답해야 한다는 강박** | 모르면 지어냄 (환각의 행동적 기원) |
| 사실을 조합해 본 경험이 없음 | 추론 연쇄가 약함 |
| 극도로 문자 그대로 해석함 | 애매한 지시는 위험 |
| 게을러질 수 있고 지름길을 찾음 | 검증 없이 믿으면 안 됨 |
| **프롬프터의 스타일을 흉내 냄** | 대충 쓰면 대충 답함 |

**노트 — 마지막 항목이 실무에서 놀랍도록 강력합니다**

"모델이 프롬프터의 스타일을 흉내 낸다"는 것은, 프롬프트를 **엉성하게 쓰면 엉성한 출력이 온다**는 뜻입니다. 문장을 완결해서 쓰고, 용어를 정확히 쓰고, 형식을 갖추면 출력의 격도 따라 올라갑니다. 이것이 L5 마지막의 "왜 톤이 그렇게 중요해 보이는가?"라는 질문과 연결됩니다.

### 3. 고등학교 연극 연출가

AI 엔지니어의 역할에 대한 비유입니다.

- 무대와 분위기를 **세팅**해야 한다
- 소품과 의상을 **제공**해야 한다
- 배우(모델)를 연기할 **마음가짐**에 놓아야 한다
- 대사의 **뉘앙스**를 가르쳐야 한다
- 인물을 **움직이게** 해야 한다

**노트 — 세 비유의 쓰임새 구분**

| 비유 | 언제 떠올리면 좋은가 |
| --- | --- |
| 비결정론적 CPU | 재현성 문제를 다룰 때 — 같은 입력이 같은 출력을 보장하지 않는다 |
| 경험 없는 인턴 | 출력이 틀렸을 때 — 왜 이런 실수를 했는지 이해할 때 |
| 연극 연출가 | 시스템 프롬프트를 설계할 때 — 무엇을 미리 세팅해야 하는지 |

## Part 2: 프롬프트의 구성 요소와 기법 (L5)

### 4. 기본 재료

| 요소 | 역할 |
| --- | --- |
| **System Prompt** | 전체 프레임 |
| **Role** | 지능 수준 / 야망 |
| **Tone** | 정중함 / 엄격함 |
| **Energy** | 긴급성 / 보상 / 벌칙 |
| **Response Structure** | 간결성 / 단순성 |
| **Guardrails** | 초점 / 주의분산 처리 / 환각 방지 |

기본 입력 구성은 **Context / Prompt / Examples / Format** 네 가지입니다.

### 5. 순서가 중요하다

| 원칙 | 설명 |
| --- | --- |
| 선형 순서 | 뒤에서 앞을 참조하게 만들지 말 것 |
| 넓은 것 → 좁은 것 | 전체 맥락에서 세부로 줌인 |
| 힌트는 주되 베끼게 하지 말 것 | 예시가 너무 구체적이면 그대로 복사함 |
| **마지막 지시에 핵심을 담을 것** | 끝부분이 강하게 작용 |

### 6. 실전 팁

| 팁 | 설명 |
| --- | --- |
| 선형 텍스트 배치 | 5,000 단어까지 |
| **지시 반복** | 중요한 것은 **최대 5회까지** 반복 |
| **데이터와 지시의 분리** | 프롬프트 인젝션 방지 |
| 평문 구조 사용 | Markdown, YAML, JSON |
| 도구 호출, "코드" 생성 | 구조화된 출력 유도 |

**노트 — "지시 반복 5회"가 왜 효과가 있는가**

이상해 보이지만 근거가 있습니다. 어텐션은 컨텍스트 전체에 분산되고, 긴 컨텍스트에서는 특정 지시의 상대적 비중이 희석됩니다. 같은 지시를 여러 위치에 배치하면 **어떤 위치에서 읽히든 걸리게** 됩니다. L6의 "Sandwiching"이 이 원리를 정식화한 것입니다.

다만 5회는 상한입니다. 더 반복하면 토큰만 낭비하고, 모델이 그 지시에 과도하게 집착해 다른 요구를 무시할 수 있습니다.

**노트 — 데이터/지시 분리와 그 한계**

강의가 예시에서 쓰는 방식은 **구분자(delimiter)**입니다.

```
... 삼중 달러 기호로 구분된 OCR 텍스트에서 ...
$$$ OCR 텍스트 $$$
```

이렇게 하면 "이 안은 데이터다"라는 신호가 강해집니다. 다만 **완전한 방어는 아닙니다.** 데이터 안에 `$$$`를 넣어 구분자를 탈출하거나, "위 지시를 무시하라"는 문장을 심는 공격이 가능합니다.

구분자는 **사고 방지**이지 보안 경계가 아닙니다. 실제 보안은 권한 최소화와 검증에서 나옵니다(Lecture 7 Part 9).

### 7. 실행 예제 — 3단계 진화

강의는 하나의 예제를 3단계로 발전시킵니다. **교통사고 경찰 보고서를 OCR해서 사건 정보를 추출**하는 작업입니다.

#### 1단계 — 소박한 프롬프트

> 이어지는 텍스트에서 부상자, 책임 당사자, 사고가 발생한 카운티를 이름으로 식별하고, 그 정보를 사용해 이 사건의 가치를 추정하라.

문제점: 역할 없음, 형식 지정 없음, 데이터 경계 없음, 판단 기준 없음.

#### 2단계 — 컨텍스트와 상세도 추가

> **당신은 도로 사고로 다친 의뢰인을 위해 가능한 최대 배상을 받아내는 데 특화된 로펌의 최고 법률 보조원입니다.**
>
> 삼중 달러 기호로 구분된 경찰 사고 보고서 OCR 텍스트에서 사고 위치를 식별하고, 책임 당사자와 부상자 **전원의 이름과 주소**를 찾으십시오. **먼저 사고 위치를 출력하고, 이어서 책임 당사자 목록을, 마지막으로 부상자 목록을** 출력하십시오.
>
> `$$$ OCR 텍스트 $$$`

추가된 것: **역할 부여 / 데이터 구분자 / 출력 순서 명시**

#### 3단계 — 예시·세부 규칙·형식 지정

- 사고 위치는 텍스트에 있으면 **카운티**까지 명시할 것
- 책임 당사자가 명확하지 않으면 **교통사고 조사에 대한 이해를 사용해** 판단할 것
- 책임 당사자가 사업체에 속하면 **그 사업체도 함께** 기재할 것
- **부상이 없으면 명확히 표시하고 더 이상 처리를 중단할 것**
- 부상자별로 **구급 처치 및 입원 여부**를 표시할 것
- 삼중 별표로 구분된 유사 판례를 근거로 최대 배상액을 추정할 것

**노트 — 3단계에서 배울 두 가지**

**(1) 조기 종료 조건이 들어갔습니다.** "부상이 없으면 중단하라"는 것은 **빈 결과를 명시적으로 허용**하는 장치입니다. 이게 없으면 모델은 없는 부상을 만들어냅니다(Part 4의 "빈 컨텍스트 = 환각 보장"과 직결).

**(2) 판단 근거를 외부에서 줍니다.** 배상액을 모델의 감으로 추정하게 두지 않고 유사 판례를 함께 넣었습니다. 이것이 곧 RAG의 축소판입니다.

## Part 3: RAG와 형식 (L5)

### 8. 언제 RAG를 추가하는가

| 조건 | 설명 |
| --- | --- |
| 관련 내용이 컨텍스트 윈도우보다 **훨씬 클 때** | 전부 넣을 수 없음 |
| 내용이 **고유·독점적**이고 어떤 학습 데이터에도 없을 때 | 모델이 알 리가 없음 |

**실무 요령 (슬라이드):**

- 적절한 크기의 **겹치는(overlapping) 청크**
- **키워드 검색과 결합**
- 최적 청크를 찾도록 프롬프팅하되
- **빈 답변(null answer)을 피하도록** 할 것

**노트 — 청킹 실무 감각**

슬라이드가 "right sized"라고만 하는 부분의 통상적 출발점입니다.

| 항목 | 통상 범위 | 이유 |
| --- | --- | --- |
| 청크 크기 | 300~800 토큰 | 너무 작으면 맥락 상실, 너무 크면 노이즈 유입 |
| 겹침(overlap) | 10~20% | 경계에서 잘린 문장을 복원 |
| 검색 개수 | 3~10개 | 많을수록 노이즈와 "lost in the middle" 위험 |

그리고 **하이브리드 검색**(임베딩 + 키워드/BM25)이 순수 벡터 검색보다 거의 항상 낫습니다. 임베딩은 의미는 잡지만 **고유명사·코드·에러 코드처럼 정확히 일치해야 하는 토큰에 약합니다.** 강의가 "키워드 검색과 결합"이라고 한 이유입니다.

### 9. 형식과 구조

> 언어 능력에 관심이 쏠려 있지만, 모델은 **형식과 구조에서도 놀라운 능력**을 보인다. — "조직 문법(organizational grammar)"

| 요점 | 내용 |
| --- | --- |
| **입력 형식도 출력 형식만큼 중요** | 예: OCR 결과를 Markdown으로 변환해 넣기 |
| **YAML을 입력 언어로** | JSON보다 나은 결과가 나오는 경우가 많음 |
| 구조화 출력을 활용 | 단, `jq` 같은 도구로 **JSON 생성이 제대로 됐는지 검사** |

**노트 — YAML이 JSON보다 나은 이유**

세 가지가 있습니다.

1. **토큰 효율** — 중괄호·대괄호·따옴표·쉼표가 전부 토큰입니다. YAML은 들여쓰기로 구조를 표현해 같은 데이터에 토큰을 덜 씁니다. 큰 페이로드에서 10~30% 차이가 납니다.
2. **읽기 쉬움** — 사람이 읽기 쉬운 형식은 모델도 파싱 오류가 적습니다.
3. **문법 오류에 관대** — JSON은 쉼표 하나 틀리면 파싱 실패입니다.

단, **출력**은 JSON이 안전합니다. 다운스트림이 엄격하게 검증할 수 있기 때문입니다. **입력은 YAML, 출력은 JSON**이 실무적 조합입니다.

## Part 4: 오류 케이스 (L5)

강의가 꼽은 네 가지 회피 대상입니다.

| 회피할 것 | 이유 | 대안 |
| --- | --- | --- |
| **숫자 연산** | 학습 데이터가 적음 | 명시적 숫자 참조는 **두 자리 이하**로 유지. 계산은 도구에게 |
| **결과에 점수 매기기** | 모델이 경험 부족 | **가능한 한 이진 판단**으로 |
| 장황한 응답과 복잡한 구조 | 뒤로 갈수록 품질 저하 | 구조화 출력과 후반부 출력을 **이중 확인** |
| **빈 데이터 컨텍스트** | **환각이 보장됨** | 빈 경우를 명시적으로 처리 |

슬라이드의 짓궂은 예시: *"13다움(13ness)이란 무엇인가? 1729다움이란? 첫 번째 지루한 수는?"* — 모델은 이런 질문에도 그럴듯한 답을 만들어 냅니다.

**노트 — "점수 대신 이진 판단"이 가장 실용적인 조언입니다**

"이 코드 품질을 1~10으로 매겨라"는 지시는 일관성이 없습니다. 같은 코드에 7을 줬다 4를 줍니다. 기준이 학습되어 있지 않기 때문입니다.

반면 "이 코드에 null 체크가 누락되었는가? 예/아니오"는 안정적입니다. **복합 판단을 여러 개의 이진 질문으로 쪼개고 집계하는 것**이 점수를 직접 요구하는 것보다 거의 항상 낫습니다. LLM-as-a-Judge를 설계할 때 이 원칙이 핵심입니다.

### 10. 목록은 계속된다 (기타 기법)

- **데이터 추출과 분석을 분리**하라
- **검토 프롬프팅**을 추가하라
- 목록 형식과 주소 표기법을 지정하라
- 모델이 **원본 문서에서만** 추출하도록 하라
- 가장 중요한 결과는 **반복하고 확인**하라
- 관련될 때는 **부정 결과도 긍정 결과만큼 중요하다**고 강조하라
- 프롬프트 확장 자체에 AI를 활용하라

**노트 — "추출과 분석을 분리하라"가 가장 중요합니다**

한 번의 호출에서 "찾아라 + 판단하라"를 동시에 시키면, 모델은 **판단에 유리하도록 추출을 왜곡**합니다. 배상액을 높게 추정하고 싶은 프롬프트에서는 부상을 과장해서 읽어냅니다.

두 단계로 나누면 1단계 출력(추출된 사실)을 사람이나 코드가 검사할 수 있고, 2단계는 검증된 사실 위에서만 판단합니다. 이것이 Lecture 7의 Prompt Chaining 패턴이 정확도를 올리는 메커니즘입니다.

## Part 5: LLM 호출에 실제로 들어가는 것 (L6)

### 11. "단순한 채팅"이라는 착각

> 사용자에게 단순한 텍스트 상자로 보이는 것은 사실 **정보 빙산의 일각**입니다. 애플리케이션은 매 턴마다 이 스택을 컴파일합니다.

#### 컴파일된 요청의 3계층

| 계층 | 내용 |
| --- | --- |
| **1. System & Persona 계층** | 정체성과 행동 경계를 정의. 모델 기본값 + 앱 로직 + 사용자 선호의 합성 |
| **2. Injected State (핵심)** | 상태 없는 모델은 아무것도 모름. 메모리·RAG 문서·파일을 **매번 새로 주입**해야 함 |
| **3. Parameters (보이지 않음)** | Temperature, Max Tokens, Logit Bias — 스택이 처리되는 방식을 지배 |

#### 스택의 실제 구성 요소

```
[System Instructions]
  ├ 모델 시스템 프롬프트   "You are GPT-4..."
  ├ 제품 시스템 프롬프트   "The user is using {AppName}..."
  └ 페르소나 / 커스텀 지시  "Be clear..."

[Tooling 계층]
  ├ 사용 가능한 도구       [searchWeb, sendEmail]
  ├ 도구 정의              JSON Schema
  └ 최근 도구 출력         searchWeb_1 returned...

[주입된 지식 상태]
  ├ 장기 메모리            "User is named John..."
  ├ 검색된 데이터 (RAG)    관련 문서 청크
  └ 사용자 제출 데이터      파일 업로드

[대화 이력]
  ├ User: "어떤 종류의 상점이..."
  ├ Assistant: "철물점은..."
  └ User (새 프롬프트): "영업 시간이..."
```

> **CS224G Insight: 모델이 한 토큰을 생성하기도 전에, "무엇을 아는가"의 90%는 당신의 애플리케이션 로직이 결정한다.**

### 12. 컨텍스트가 결과를 어떻게 바꾸는가 — 3단계 예시

| 수준 | 질의 | 결과 |
| --- | --- | --- |
| **Level 1** 나쁜 프롬프트 + 나쁜 컨텍스트 | "헌혈이 건강에 좋나요?" | 일반적인 WebMD식 조언 |
| **Level 2** 좋은 프롬프트 + 나쁜 컨텍스트 | "헌혈이 높은 SHBG 수치에 도움이 되나요?" | 이론적 답변, 개인화 없음 |
| **Level 3** 좋은 프롬프트 + 좋은 컨텍스트 | 위 질문 + **첨부: 2023~2025 혈액 검사 이력, 헌혈 날짜, 유전자 검사 결과** | 실제 수치를 헌혈 시점과 대조한 고도로 개인화된 분석 |

> **핵심: 더 나은 프롬프트 + 더 나은 컨텍스트 = 극적으로 더 나은 결과**

## Part 6: 파라미터와 토큰 예산 (L6)

### 13. 숨은 제어 레버

| 파라미터 | 범위 | 역할 |
| --- | --- | --- |
| **Temperature** | 0.0 ~ 2.0 | 무작위성/창의성. 0.0이면 결정론적, 1.0이면 창의적이나 불안정 |
| **Max Tokens** | 정수 | 생성 길이의 하드 리밋. **입력이 아니라 출력만** 제한. 비용·지연시간 통제에 핵심 |
| **Logit Bias** | `Map<Token, Float>` | 외과적 정밀 도구. 특정 토큰을 강제로 회피/선호. **분류 일관성**에 자주 사용 |

### 14. 토큰 예산 경제학

| 항목 | 내용 |
| --- | --- |
| 환산 규칙 | **1 토큰 ≈ 0.75 단어** (1,000 토큰 ≈ 750 단어) |
| 성질 | 모델은 단어가 아니라 토큰을 봄. 컨텍스트 한계는 **엄격한 하드 스톱** |
| 압축 트레이드오프 | 프론트엔드는 이력을 요약하거나 오래된 메시지를 잘라야 함. **공간을 얻고 충실도를 잃음** |

### 15. Lost in the Middle 현상

> 컨텍스트가 차오를수록 성능이 저하됩니다. 10만 토큰 넘는 윈도우의 **중간에 묻힌 핵심 지시는 종종 무시됩니다.**

**노트 — 원 논문과 실제 곡선 모양**

Liu et al., *"Lost in the Middle: How Language Models Use Long Contexts"* (2023)에서 정식으로 측정된 현상입니다.

핵심 발견은 정확도가 문서 위치에 대해 **U자 곡선**을 그린다는 것입니다.

```
정확도
  높음 ┤ ●                                    ●
       │   ●                              ●
       │      ●                      ●
  낮음 ┤          ●  ●  ●  ●  ●  ●
       └─────────────────────────────────────
        앞          ←  중간  →           뒤
```

- **맨 앞**(primacy)과 **맨 뒤**(recency)에 있는 정보는 잘 활용됨
- **중간**은 급격히 떨어짐 — 심한 경우 검색을 아예 안 한 것보다 못함

실무 함의가 큽니다. **RAG로 문서를 10개 넣으면 3~7번째 문서는 사실상 낭비**일 수 있습니다. 개수를 늘리는 것보다 **재순위화(re-ranking)로 정말 관련 있는 3개만 앞뒤에 배치**하는 편이 낫습니다.

### 16. Sandwiching

> **핵심 지시를 컨텍스트 윈도우의 시작(System)과 끝(User) 양쪽에 배치해 "lost in the middle"에 대응하라.**

L5의 "지시를 최대 5회 반복하라"가 여기서 원리적으로 설명됩니다.

## Part 7: 지시의 3계층 (L6)

| 계층 | 이름 | 통제 주체 | 예시 |
| --- | --- | --- | --- |
| 1 | **Model System Prompt** | 불변 (제공자) | "You are GPT-4, a helpful assistant developed by OpenAI..." |
| 2 | **Product System Prompt** | **개발자** | "The user is using {AppName} to analyze financial data..." |
| 3 | **Personas / Custom Instructions** | 사용자 | "간결하게. JSON으로 답할 것. 수학은 파이썬 선호." |

### 17. 모범 사례

| 사례 | 설명 |
| --- | --- |
| **Sandwiching** | 핵심 지시를 시작과 끝 양쪽에 |
| **관심사 분리** | **보안 가드레일은 2계층(제품 프롬프트)에 두어** 사용자가 3계층에서 쉽게 무력화하지 못하게 할 것 |

### 18. 과소평가된 레버 — 페르소나

- 대부분의 프론트엔드가 이 설정을 깊이 숨겨두지만, 파워 유저와 복잡한 앱에서는 **사용자가 전역 불변식을 정의하게 하는 것이 중요**합니다
- "마크다운으로 형식화하라"를 매 프롬프트마다 반복하는 대신 **페르소나 계층에 한 번 넣으십시오.** 프롬프트 노이즈가 줄고 준수율이 올라갑니다

**노트 — 2계층에 가드레일을 두라는 조언의 무게**

이것은 보안 설계 원칙입니다. 사용자가 편집할 수 있는 계층에 안전 규칙을 두면, 사용자가 그것을 지우거나 덮어쓸 수 있습니다. **권한이 다른 지시는 다른 계층에 두어야** 합니다.

다만 앞서 말했듯 이것도 완전한 경계는 아닙니다. 세 계층 모두 결국 하나의 텍스트로 합쳐져 모델에 들어가며, 모델은 계층을 문법적으로 구분하지 않습니다. **강한 관례이지 강제된 경계가 아닙니다.**

## Part 8: 주입되는 지식 (L6)

> **핵심 멘탈 모델: LLM은 상태 없는 "병 속의 뇌(brain-in-a-jar)"다.** 아무것도 기억하지 못한다. 메모리는 **모델 계층이 아니라 애플리케이션 계층의 기능**이다.

| 종류 | 설명 | 예시 |
| --- | --- | --- |
| **1. 보존된 메모리** | 세션을 넘어 유지되는 사용자에 대한 장기 상태 | "사용자 이름은 John, 캘리포니아 거주, 스탠퍼드에서 강의, 간결한 코드 선호" |
| **2. 검색된 데이터 (RAG)** | 호출 전에 연결된 데이터스토어에서 가져온 데이터. **모델이 검색하는 게 아니라 인프라가 검색해 주입** | 관련 문서 청크 |
| **3. 사용자 제출 데이터** | 임시 파일이나 프로젝트 첨부 | "이 PDF를 분석해 줘" |

**아키텍처 예시 (고객 지원 에이전트):**
앱이 질의 주제로 내부 지식베이스를 검색 → 상위 3개 문서 확보 → 텍스트를 컨텍스트에 주입 → 모델이 응답 생성

## Part 9: 도구 = 프로그래밍 가능한 컨텍스트 (L6)

> 도구는 마법이 아닙니다. **스키마로 감싼 평범한 함수(API 호출, 스크립트)**일 뿐입니다.

> **LLM은 코드를 실행하거나 웹을 검색하지 않습니다. 의도를 나타내는 토큰을 내보낼 뿐이고, 실제 작업은 오케스트레이터(당신의 앱)가 합니다.**

**에이전트 루프:**

```
오케스트레이터가 도구 실행 → 출력이 새 컨텍스트가 됨 → LLM에 되먹임 → 끝날 때까지 반복
```

#### 실행 흐름 전체

```
사용자 프롬프트 (입력 + 첨부)
        ↓
   오케스트레이터 (당신의 앱)
        ├── DB에 메모리 질의 → 반환
        ├── RAG 검색 질의     → 결과
        ├── 시스템 프롬프트 구성
        └── 도구 정의 + 파라미터
        ↓  모든 컨텍스트를 실은 LLM 호출 디스패치
   LLM (Claude Sonnet 4.5, OpenAI o3, Grok 4, Gemini 2.5 Pro, ...)
        ↓  결과를 반환하거나 "도구 호출 토큰"을 내보냄
   오케스트레이터가 도구 실행 → 결과 반환 → 루프
        ↓
   사용자에게 응답 전송
```

**노트 — Lecture 7과 같은 그림입니다**

이 흐름은 Lecture 7의 "Stop Reason" 설명과 정확히 같은 내용을 컨텍스트 관점에서 다시 그린 것입니다. 두 강의를 같이 보면 **도구 = 컨텍스트를 프로그램으로 채우는 방법**이라는 통합된 관점이 생깁니다.

RAG가 "미리 정해둔 것을 가져오는 것"이라면, 도구 호출은 **"모델이 필요하다고 판단했을 때 가져오는 것"**입니다. 후자가 훨씬 강력하지만 예측 가능성이 떨어집니다 — 다시 워크플로우 vs 에이전트의 트레이드오프입니다.

## Part 10: 당신이 통제할 수 있는 다섯 가지 레버 (L6)

> 모델 가중치나 학습 데이터는 불투명하지만, **이 다섯은 애플리케이션 개발자의 직접 통제 아래** 있습니다.

| # | 레버 | 실무 지침 |
| --- | --- | --- |
| 1 | **페르소나 / 커스텀 지시** | 전역 불변식을 여기 정의 ("항상 JSON 반환"). 매 프롬프트마다 반복하지 말 것 |
| 2 | **사용 가능한 도구** | **도구를 큐레이션할 것.** 모델에게 50개를 주면 혼란스러워한다. 그 작업에 실제로 필요한 5개만 |
| 3 | **RAG / 데이터스토어 연결** | 검색 품질은 당신이 통제한다. 어떤 DB를 연결했는가? 청크를 어떻게 검색하는가? **거대한 성능 레버** |
| 4 | **사용자 제출 데이터** | 파일 업로드를 장려할 것. **명시적 컨텍스트("이 PDF를 읽어라")가 암묵적 검색을 항상 이긴다** |
| 5 | **당신의 프롬프트** | 여전히 중요하다. 단 **최종 지시**로 다룰 것이지 컨텍스트 페이로드 전체가 아니다 |

> **Builder's Tip: 프롬프트만 만지지 말고, 프롬프트를 둘러싼 입력을 엔지니어링하라.**

**노트 — 2번이 에이전트 설계에서 특히 중요합니다**

"도구 50개는 혼란스럽다"는 관찰은 실측된 현상입니다. 도구가 늘어나면 (1) 도구 정의가 컨텍스트를 차지하고 (2) 유사한 도구 사이에서 선택 오류가 늘어납니다.

대응은 **작업에 따라 도구 세트를 동적으로 바꾸는 것**입니다. 라우팅으로 작업 유형을 먼저 판정하고, 그 유형에 필요한 도구만 노출하는 방식입니다. Lecture 7의 Routing 패턴이 여기서도 쓰입니다.

## Part 11: 토큰 예산 위기 — 축출 정책 (L6 토론 주제)

> 장시간 실행되는 에이전트 대화가 128k 컨텍스트 한계에 도달하고 있습니다. 성능이 저하되고 있습니다. **당신의 축출 정책(eviction policy)은 무엇입니까?**

강의가 던진 세 가지 질문입니다.

#### 1. 압축 vs 축출

이력을 **요약(손실 압축)**할 것인가, 오래된 턴을 **버릴(축출)** 것인가? 그 이유는?

| 방식 | 장점 | 단점 |
| --- | --- | --- |
| **압축(Compaction)** | 오래된 정보의 요지를 유지 | LLM 호출 비용 발생, 요약 과정에서 왜곡 가능 |
| **축출(Eviction)** | 비용 0, 단순 | 버린 정보는 영영 사라짐 |

#### 2. 반드시 고정해야 할 것

어떤 컨텍스트는 절대 버려선 안 됩니다 — 시스템 지시, 도구 정의 등.

#### 3. 재검색 전략

컨텍스트에서 파일을 버렸다면, 나중에 필요할 때 모델이 어떻게 다시 가져오는가?

**노트 — 실무의 표준 답안**

세 질문에 대한 일반적인 조합은 이렇습니다.

| 컨텍스트 종류 | 정책 |
| --- | --- |
| 시스템 지시 · 도구 정의 | **고정(pin).** 절대 축출 안 함 |
| 최근 N턴 | 원문 유지 |
| 오래된 턴 | **압축** — 요약해서 한 덩어리로 |
| 대용량 첨부 파일 | **축출 + 재검색 경로 확보.** 컨텍스트에서 빼되 도구로 다시 읽을 수 있게 |
| 도구 출력 | 대체로 축출 가능 — 결론만 요약에 남김 |

3번 질문의 답이 특히 중요합니다. **버릴 수 있으려면 다시 가져올 수 있어야 합니다.** 파일을 컨텍스트에서 빼더라도 `read_file(path)` 도구가 있으면 모델이 필요할 때 다시 읽습니다. 재검색 경로가 없으면 축출은 영구적 정보 손실이 됩니다.

## 핵심 요약

### 마무리 인용

> "LLM을 새로 온 천재 박사급 팀원이라고 생각하십시오 — **다만 언제나 첫 출근날인** 팀원." — Andy Bromberg

### 강의의 네 가지 결론 (L6 슬라이드)

| # | 결론 |
| --- | --- |
| 1 | **Context Engineering > Prompt Engineering** — 프롬프트는 창끝일 뿐. 주변 컨텍스트가 질문의 표현보다 성능을 더 좌우한다 |
| 2 | **컨텍스트는 컴파일된 산출물이다** — "대화"가 아니라, 앱이 매 턴 거대한 텍스트 파일을 컴파일하는 것 |
| 3 | **상태는 모델이 아니라 앱에 있다** — LLM은 병 속의 뇌. 모든 "기억"은 인프라가 검색해 주입한다 |
| 4 | **다섯 레버를 다 쓰라** — 페르소나, 도구, RAG, 업로드, 프롬프트. 마지막 하나만 만지지 말 것 |

### 한 문장으로 압축

| 주제 | 결론 |
| --- | --- |
| 모델을 보는 눈 | 똑똑하지만 **언제나 첫 출근날인** 인턴 |
| 순서 | 넓은 것 → 좁은 것. **마지막 지시가 강하다** |
| 반복 | 중요한 건 최대 5회. 시작과 끝에 배치(**Sandwiching**) |
| 데이터/지시 | 구분자로 분리 — 단 **보안 경계가 아니라 사고 방지** |
| 형식 | 입력은 YAML이 유리, 출력은 JSON + 검증 |
| 회피 | 숫자 연산 · 점수 매기기 · **빈 컨텍스트(= 환각 보장)** |
| 분리 | **추출과 분석을 분리하라** |
| 긴 컨텍스트 | **Lost in the Middle** — 개수보다 재순위화 |
| 통제 가능한 것 | 페르소나 · 도구 · RAG · 업로드 · 프롬프트 |
| 축출 | 지시는 고정, 오래된 턴은 압축, 파일은 축출 + **재검색 경로 확보** |

## 용어 정리

| 용어 | 의미 |
| --- | --- |
| Context Engineering | 모델에게 공급되는 정보 전체를 설계하는 것 |
| Compiled Request | 앱이 매 턴 조립해 모델에 보내는 전체 텍스트 |
| Injected State | 매 호출마다 새로 주입해야 하는 메모리·RAG·첨부 |
| Brain-in-a-Jar | 상태 없는 LLM을 가리키는 비유 |
| Lost in the Middle | 긴 컨텍스트 중간의 정보가 무시되는 현상 (U자 곡선) |
| Sandwiching | 핵심 지시를 시작과 끝 양쪽에 배치하는 기법 |
| Temperature | 출력 분포의 무작위성 조절 (0.0~2.0) |
| Logit Bias | 특정 토큰의 확률을 강제로 조정하는 파라미터 |
| Eviction | 컨텍스트에서 오래된 항목을 버리는 것 |
| Compaction | 오래된 이력을 요약해 압축하는 것 |
| Pinning | 절대 축출하지 않도록 고정하는 것 |
| Hybrid Search | 임베딩 검색 + 키워드 검색의 결합 |
| Re-ranking | 검색된 후보를 다시 정렬해 상위만 남기는 단계 |
| Prompt Injection | 데이터에 숨긴 지시로 모델을 탈취하는 공격 |
