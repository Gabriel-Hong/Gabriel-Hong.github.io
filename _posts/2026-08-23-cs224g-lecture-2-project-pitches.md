## 강의 개요

수업 운영 안내가 대부분이지만, **3분 피칭을 어떻게 하는가**와 **어떤 프로젝트가 좋은 프로젝트인가**에 대한 부분은 그대로 실무에 쓸 수 있습니다. 이 노트는 그 두 가지만 정리하고, 관련이 깊은 Lecture 1의 프로젝트·팀 선정 기준을 부록으로 붙였습니다.

## Part 1: 스타트업 프로젝트에 대한 안목

### 1. 새로운 기술 파도

> IC → PC → 네트워킹 → 웹 → 웹 2.0 → 모바일 → 크립토 → **AI**

### 2. 곡선보다 **살짝** 앞서기

> 너무 앞서면 소용없다 — **서핑이 정말 좋은 비유다.**

강사의 자기 경험:
- 30년 전에 GAN 기법을 예고하는 책 챕터를 썼다
- 15년 전에 AI로 돌아오기 시작했다

### 3. 필요한 감각

> **트렌드에 대한 각성, 그리고 시장/제품의 공백에 대한 각성**

**노트 — 서핑 비유를 조금 풀면**

파도가 오기 전에 패들링을 시작해야 하지만, 너무 일찍 시작하면 파도가 오기 전에 지나가 버립니다. 너무 늦으면 파도가 이미 지나갑니다.

기술 프로젝트에서 "너무 앞선다"는 실패는 흔합니다 — 기술은 맞았는데 **주변 인프라·사용자 습관·비용 구조가 아직 안 따라온** 경우입니다. GAN을 30년 전에 예고한 사람이 그때 창업했다면 실패했을 것입니다.

반대로 "지금이 파도의 어디쯤인가"를 판단하는 실용적 신호는 **주변에서 비슷한 시도가 여러 개 동시에 보이기 시작하는 시점**입니다. 하나도 없으면 이르고, 이미 승자가 있으면 늦습니다.

## Part 2: 프로젝트 제안서 — 1페이지

> **딱 1페이지!**

| 항목 | 비고 |
| --- | --- |
| 팀/프로젝트 이름 | |
| 팀원 (이름과 학번) | |
| **1줄 설명** | **3~12단어** |
| **1문단 초록** | |
| **타깃 고객/사용자는 누구인가?** | |
| 제안 일정과 마일스톤 | |

**노트 — "1줄 설명 3~12단어"라는 제약**

12단어 안에 못 넣으면 아직 정리가 안 된 것입니다. 그리고 이 한 줄이 나중에 팀원 모집, 리뷰어 설득, 스코프 방어에 계속 쓰입니다.

흔한 실패는 **기술을 설명하는 것**입니다. "LangGraph 기반 멀티에이전트 파이프라인"은 무엇을 하는지 말하지 않습니다. "회의록에서 개발 명세를 만들어 PR까지 낸다"가 12단어짜리 설명입니다.

**"타깃 고객/사용자는 누구인가"**도 의도적으로 들어간 항목입니다. 이게 비어 있으면 대부분 "만들면 좋을 것 같아서" 하는 프로젝트입니다.

## Part 3: 3분 안에 피칭하기 ⭐

강의가 제시한 다섯 요소입니다.

| # | 요소 | 내용 |
| --- | --- | --- |
| 1 | **문제를 날카롭게** | **X는 형편없다 / 느리다 / 지루하다 / 복잡하다 / 비효율적이다 / 비싸다** — 최소 하나는 고를 것 |
| 2 | **청중을 끌어들여라** | 어쩌면 질문을 던져라 |
| 3 | **엘리베이터 피치** | **듣고 나면 이것 없이는 못 살 정도로** |
| 4 | **왜 합류해야 하는지 말하라** | **당신의 초능력**은 무엇이고, 어떤 사람을 찾는가 |
| 5 | **보너스: 데모** | |

**노트 — 1번의 형용사 목록이 실용적입니다**

"X는 형편없다/느리다/지루하다/복잡하다/비효율적이다/비싸다" — 여섯 개 중 **최소 하나를 고르라**는 것은 문제를 **한 축으로 압축하라**는 뜻입니다.

문제를 여러 개 나열하면 청중은 아무것도 기억하지 못합니다. "이 일은 느리다"만 남기면 해결책도 "빠르게 만든다"로 선명해지고, 성공 지표도 자동으로 정해집니다(시간).

그리고 이 여섯 개는 **측정 가능한 축**이라는 공통점이 있습니다. "X는 좋지 않다"는 축이 없어서 개선을 증명할 수 없습니다.

**노트 — 4번이 이 목록에서 가장 자주 빠지는 항목입니다**

발표자는 보통 문제와 해결책까지만 말하고 끝냅니다. 그런데 이 피칭의 목적은 **팀원 모집**입니다 — "왜 당신이 이걸 할 수 있는가"와 "어떤 사람이 필요한가"가 없으면 듣는 사람이 자기가 낄 자리를 못 찾습니다.

사내 제안에서도 같습니다. 승인만 받고 끝나는 제안과, 사람들이 참여하고 싶어 하는 제안의 차이가 대개 여기서 갈립니다.

**노트 — 3분이라는 제약**

3분이면 대략 **450~500단어**입니다. 슬라이드 2장. 다섯 요소에 나누면 각 30~40초입니다.

즉 배경 설명을 할 시간이 없습니다. **첫 문장에서 바로 문제로 들어가야** 합니다. Lecture 1의 발표 지침(아래 부록)에 "매끄러운 전환 — 힘들이지 않게 보이도록 연습하라"가 있는 이유입니다.

## 부록: 좋은 프로젝트와 좋은 팀 (Lecture 1)

피칭과 직결되는 내용이라 Lecture 1에서 가져왔습니다.

### 4. 무엇이 훌륭한 프로젝트를 만드는가

| 축 | 내용 |
| --- | --- |
| **Impact (영향)** | 실제 사람들의 실제 문제를 푸는가<br>**LLM이 의미 있는 해법을 가능하게 하는 지점인가** |
| **Realistic scope (현실적 범위)** | 위험이 한정되어 있는가<br>10주 과정에 맞는 크기인가<br>**의미 있는 중간 마일스톤이 있는가** |
| **Team fit (팀 적합성)** | 무엇이 당신을 계속 신나게 할 것인가<br>**이미 아는 것 + 배우고 싶은 것**의 조합 |

### 5. 무엇이 훌륭한 팀을 만드는가

| 축 | 내용 |
| --- | --- |
| **팀 크기 2~4** | 2명은 가능하지만 힘들다 / **3~4명이 최적** / **5명이면 최소 한 명은 제 몫을 안 한다** |
| **상호보완적 스킬셋** | 백엔드, 프론트엔드, 디자인, 제품 관리, 커뮤니케이션<br>**이 전부에 강한 커버리지가 있는지 확인할 것** |
| **정렬(Alignment)** | 관심 영역 / 철학 / **몰입 수준과 업무 기대치** |

**노트 — "5명이면 최소 한 명은 제 몫을 안 한다"**

거칠지만 경험적으로 맞는 말입니다. 링겔만 효과(집단이 커질수록 개인의 기여도가 떨어지는 현상)의 실무 버전입니다.

그리고 **"이미 아는 것 + 배우고 싶은 것"**이라는 조합 기준이 좋습니다. 전부 아는 것만 하면 지루하고, 전부 모르는 것을 하면 완성하지 못합니다.

### 6. 애자일 프로젝트 방법론

- 빠르게 뭔가를 만들어 낸다
- 목요일에 발표한다
- Slack에서 사람들과 이야기한다
- **비슷한 제안과 관심사를 찾는다**
- 대화를 바탕으로 다듬고 수정한다
- 맞는 팀을 구성한다
- **반복 횟수가 많을수록 거의 항상 더 나은 결과가 나온다**

### 7. 발표의 목표 (Lecture 5 도입부에서)

| 목표 |
| --- |
| **청중을 끌어들여라** |
| **매끄러운 전환** (힘들이지 않게 보이도록 연습하라) |
| **기억에 남게/밈이 되게** (재미있게, 예상 밖으로, 요점만) |
| **당신의 이야기를 하라** (지금, 계획, 결과) |
| **다음 발표가 기대되게 만들어라** |

그리고 팀 발표 구성(3분, 슬라이드 2장):

| 시간 | 내용 |
| --- | --- |
| 30초 | 누구를 위해 어떤 문제를 푸는가 |
| 30초 | 당신의 해법 |
| **60초** | **빠른 데모** (스크린샷, 영상) |
| 30초 | **계획 대비 실제** |
| 30초 | 배운 것 중 독특하거나 흥미로운 것 |

**노트 — "계획 대비 실제(plan vs actual)"에 30초를 배정한 게 특이합니다**

보통 발표에서는 성공만 말합니다. 이 과정은 **계획과 실제가 어떻게 달랐는지**를 발표 구성에 명시적으로 넣습니다.

이유는 두 가지로 보입니다. 첫째, 그게 청중에게 가장 유용한 정보입니다 — 남의 성공보다 남이 어디서 막혔는지가 배울 게 많습니다. 둘째, **그것을 말해야 한다는 걸 알면 계획을 더 정직하게 세우게 됩니다.**

## 핵심 요약

### 피칭 체크리스트

```
[ ] 1줄 설명이 3~12단어인가?           ← 기술이 아니라 무엇을 하는지
[ ] 타깃 사용자가 명시되어 있는가?
[ ] 문제를 한 축으로 압축했는가?         ← 느리다/비싸다/복잡하다 중 하나
[ ] 첫 문장에서 바로 문제로 들어가는가?   ← 3분엔 배경 설명할 시간 없음
[ ] 데모가 있는가?                     ← 60초
[ ] 왜 합류해야 하는지 말했는가?         ← 내 초능력 + 찾는 사람
[ ] 계획 대비 실제를 말할 준비가 됐는가?
```

### 한 문장으로 압축

| 주제 | 결론 |
| --- | --- |
| 타이밍 | **곡선보다 살짝 앞서기.** 너무 앞서면 소용없다 (서핑) |
| 1줄 설명 | **3~12단어.** 기술이 아니라 하는 일을 |
| 문제 제시 | **한 축으로 압축** — 느리다/비싸다/복잡하다 중 최소 하나 |
| 왜 그 축인가 | 여섯 형용사가 전부 **측정 가능한 축**이기 때문 |
| 가장 자주 빠지는 것 | **"왜 합류해야 하는가"** — 초능력과 찾는 사람 |
| 3분 배분 | 문제 30초 / 해법 30초 / **데모 60초** / 계획 대비 실제 30초 / 배운 것 30초 |
| 좋은 프로젝트 | 영향 · **현실적 범위** · 팀 적합성 |
| 좋은 팀 | **3~4명**, 상호보완 스킬, 몰입 수준의 정렬 |
| 반복 | **반복 횟수가 많을수록 거의 항상 더 나은 결과** |

### 가장 중요한 두 문장

1. **"X sucks, is slow, tedious, complicated, inefficient, expensive — pick at least 1."**
2. **"Tell us why we should join you — your superpower, who you look for."**
