## Part 1: AI-Native란 무엇인가

### 1. 가장 빠른 사람들이 하고 있는 것

강의가 인용한 발언들입니다.

| 인물 | 발언 |
| --- | --- |
| Andrej Karpathy (2025.12) | "이 직업은 극적으로 재구성되고 있다" |
| Dario Amodei, Anthropic CEO (2025.03) | "AI가 코드의 90%를 쓰게 될 것이다" |
| Kent Beck, TDD 창시자 (2025.12) | "AI가 탐색 공간을 붕괴시킨다. 며칠 걸리던 작업이 몇 시간이 된다" |
| Boris Cherny, Claude Code 개발자 (2026.01) | "Claude Code의 80~90%가 Claude Code로 작성된다" |
| Theo (t3.gg) (2025.12) | "코드의 70~90%가 이제 직접 생성된다" |

> 이건 과장이 아닙니다. **지금 최상위 수행자들이 실제로 하고 있는 일**입니다.

### 2. AI-Native가 **아닌** 것

| ✗ | 예시 |
| --- | --- |
| ✗ | "우리는 고객 지원에 ChatGPT를 씁니다" |
| ✗ | "우리 사이트에 AI 챗봇이 있습니다" |
| ✗ | "우리 엔지니어들은 Copilot을 씁니다" |
| ✗ | "모델을 한 번 파인튜닝했습니다" |

> 이것들은 **AI-assisted**입니다. AI-native가 아닙니다.

### 3. AI-Native인 것

> **AI가 일급 실행 계층(first-class execution layer)인 시스템 설계.**
>
> 당신이 쓰는 도구가 아니라, **일을 하는 행위자(actor)**.

#### 판별 테스트

> **비정형 입력이 사람 개입 없이 실행된 작업 산출물이 될 수 있는가?**
>
> 회의록 → 코드 → 커밋 → PR

**노트 — 이 테스트를 우리 상황에 적용하면**

"zero human in the loop"는 최종 목표지 시작점이 아닙니다. 강의 뒷부분(Part 3)에서 결국 **사람은 어려운 케이스만 본다**는 형태로 수렴합니다.

그래서 이 테스트는 "사람을 완전히 빼라"가 아니라 **"경로가 처음부터 끝까지 자동으로 연결되어 있는가"**를 묻는 것으로 읽는 게 맞습니다. 중간에 사람이 수동으로 형식을 바꿔 붙여넣는 단계가 있으면 그건 파이프라인이 아니라 도구 모음입니다.

## Part 2: 자동화 컨설팅 파이프라인 ⭐

### 4. 파이프라인 구조

```
📥 비정형 입력            회의록, Slack, 녹취록
        ↓
🧠 Spec Generator        Claude → 구조화된 명세
        ↓
📋 Task Manager          컨텍스트 보관
        ↓
⚡ Executor              Claude Code
        ↓
   커밋 · PR · 테스트
```

**입력 예시:**
> "Acme와의 통화에서 — 금요일까지 로그인이 되어야 한다고 함. JWT면 충분. Sam이 비밀번호에 bcrypt 언급함."

**출력:**
```
✓ src/auth/jwt.py 생성됨
✓ tests/test_auth.py 통과
```

### 5. 명세(Spec) 포맷 ⭐

강의가 제시한 실제 포맷입니다. **네 개 섹션**으로 구성됩니다.

| 섹션 | 역할 |
| --- | --- |
| **Context** | 어디에서, 무엇을 |
| **Done When** | **검증 가능한 체크리스트** |
| **Requirements** | 제약과 이미 내려진 결정 |
| **Key Files** | 명시적 범위 |

```markdown
Repo: ~/git/acme-api
Client: acme_corp
Intent: Add JWT-based user authentication to the REST API

## Done When
- [ ] POST /api/auth/login accepts email/password, returns JWT
- [ ] POST /api/auth/register creates user with hashed password
- [ ] Protected routes return 401 without valid token
- [ ] Token expiry is enforced (24h)
- [ ] All tests pass with `pytest tests/`

## Requirements
- JWT tokens with 24-hour expiry
- bcrypt for password hashing (cost factor 12)
- Return 401 for invalid credentials
- Email must be unique, validated format

## Key Files
Files to create:
- src/auth/jwt.py       - Token creation/validation
- src/routes/auth.py    - Login/register endpoints
- tests/test_auth.py    - Auth tests
Files to modify:
- src/main.py           - Register auth routes
- src/models/user.py    - Add password_hash field
```

### 6. 왜 이게 작동하는가

| 속성 | 내용 |
| --- | --- |
| **Checkable** | 모든 "Done When" 항목을 테스트할 수 있다 |
| **Scoped** | 핵심 파일이 명시적으로 나열되어 있다 |
| **Contextual** | 아키텍처가 미리 결정되어 있다 |
| **Executable** | 에이전트가 자율적으로 실행할 수 있다 |

**노트 — `Done When`이 이 포맷의 심장입니다**

네 섹션 중 하나만 남긴다면 이것입니다. 이유는 세 가지입니다.

**(1) 검증 루프의 입력이 된다.** "Done When" 항목이 전부 테스트 가능하면, 그 목록이 곧 에이전트의 종료 조건이자 평가 기준이 됩니다. Lecture 7의 Evaluator, Lecture 11의 "검증은 단일 최대의 품질 배수"가 여기에 연결됩니다.

**(2) 애매한 요구를 강제로 드러낸다.** "로그인이 잘 되어야 한다"는 체크리스트로 쓸 수 없습니다. 쓰려고 하는 순간 "토큰 만료는 몇 시간인가"를 물어야 하고, 그게 기획 단계에서 결정됩니다. **명세를 검증 가능하게 쓰는 행위 자체가 기획을 완성시킵니다.**

**(3) 완료 판정에 논쟁이 없어진다.** 사람 검토 게이트에서 "이게 다 된 건가?"를 두고 왕복하는 비용이 사라집니다.

**노트 — Key Files가 왜 필요한가**

에이전트에게 "알아서 찾아 고쳐라"라고 하면 범위가 통제되지 않습니다. 관련 없는 파일을 건드리거나, 리팩터링을 시작하거나, 같은 로직을 새 파일에 중복 구현합니다.

**생성할 파일 / 수정할 파일을 미리 나열**하면 범위가 고정되고, 리뷰어도 diff가 예상 범위 안인지 즉시 판단할 수 있습니다. 대형 레거시 코드베이스일수록 효과가 큽니다.

### 7. 실행 예시

```bash
# 회의록에서 명세 생성
python pipeline.py spec notes.txt

# 대상 저장소에서 명세 실행
python execute_spec.py \
   --spec spec.md \
   --repo ~/git/client-project \
   --pr

# 출력:
# ✓ Spec validated
# ✓ 3 files created, 2 files modified
# ✓ Tests passing
# ✓ PR created: github.com/acme/api/pull/47
```

첫 줄 `✓ Spec validated`에 주목할 만합니다. **명세 자체를 실행 전에 검증**합니다.

### 8. 비밀 관리 — secret-agent

에이전트 워크플로용 오픈소스 CLI 볼트입니다.

| 원칙 | 내용 |
| --- | --- |
| **비밀은 컨텍스트에 절대 안 들어감** | 환경변수로 주입 |
| **트레이스를 안전하게 로깅** | 로그에 비밀이 남지 않음 |
| **출력 자동 마스킹** | 유출 방지 |

{% raw %}
```bash
# 비밀을 환경변수로 — 프롬프트에 절대 넣지 않음
secret-agent exec --env API_KEY python app.py

# 명령에 템플릿으로 주입
secret-agent exec curl -H 'Bearer {{API_KEY}}' https://api.com
```
{% endraw %}

`github.com/paperMoose/secret-agent`

**노트 — 이 문제는 반드시 만납니다**

에이전트 시스템에서 자격증명은 두 군데로 샙니다. **(1) 프롬프트 컨텍스트**, **(2) 실행 트레이스 로그**. 후자가 더 위험합니다 — 디버깅하려고 남긴 로그에 토큰이 평문으로 들어가고, 그 로그가 다시 평가 데이터셋이 되는 경로가 생기기 때문입니다.

Lecture 18의 "에이전트에게 자격증명을 주면 폭발 반경이 거대해진다"와 짝을 이루는 실무 대응입니다.

### 9. 컨텍스트는 감가가 아니라 증가하는 자산

| 시점 | 사람 개입 없는 정확도 |
| --- | --- |
| 1주차 | 20% |
| 4주차 | 50% |
| 8주차 | 80% |
| 12주차 | **95%** |

> 매 상호작용이 컨텍스트에 쌓입니다 — 클라이언트 선호가 축적되고, 과거 결정이 미래를 안내하고, **쓸수록 좋아집니다.**
>
> **당신의 컨텍스트 파일이 당신의 해자입니다.**

**노트 — Lecture 15와 정확히 같은 주장입니다**

Lecture 15의 "데이터 플라이휠"과 "메모리 레이어"를 개발 파이프라인에 적용한 형태입니다. 다만 여기서는 축적 대상이 사용자 선호가 아니라 **프로젝트 규약과 과거 결정**입니다.

Lecture 11의 `agents.md` 패턴("에이전트가 실수하면 문서화하라 → 다시 반복하지 않는다")이 이 곡선을 만드는 메커니즘입니다. 세 강의가 같은 지점을 다른 각도에서 말하고 있습니다.

## Part 3: 에이전트 평가 ⭐⭐

> **프롬프트 주도 먼저, 오류 주도 나중.**

### 10. 실패는 두 종류다

| | **Spec 실패** | **일반화(Generalization) 실패** |
| --- | --- | --- |
| 원인 | 프롬프트가 불완전하거나 불명확 | 모델이 규칙을 새 상황으로 확장하지 못함 |
| 예시 | "짧게 싱크 잡아줘" → 모델이 60분으로 추측 (15분을 의도했음) | 프롬프트가 엣지 케이스 20개를 완벽히 커버 → 21번째에서 깨짐 |
| 대응 | ✓ **더 나은 프롬프트로 고칠 수 있음** | ⚠ **사람에게 라우팅하거나 한계를 수용** |

**노트 — 이 구분이 이 강의의 가장 큰 기여입니다**

에이전트가 틀렸을 때 사람들은 보통 프롬프트를 고칩니다. 그런데 **고칠 수 있는 실패와 없는 실패를 구분하지 않으면** 프롬프트가 무한히 길어지면서 서로 충돌하기 시작합니다(아래 "벽에 부딪혔다는 신호").

먼저 분류하고, 고칠 수 있는 것만 고치고, 나머지는 **탐지해서 사람에게 넘기는 것**이 올바른 순서입니다.

### 11. Phase 1 — 프롬프트 주도 평가

> **당신의 프롬프트가 곧 테스트 명세다.**

1. 프롬프트의 모든 규칙 → **테스트 가능한 assertion**으로
2. 프롬프트 자체에서 테스트 케이스를 생성
3. 모델을 실행 → 실패가 문제를 드러냄
4. 분류: **spec 이슈인가, 일반화 이슈인가?**

#### 실패 분류 흐름

```
              테스트 실패
                  ↓
      이 동작이 프롬프트에 있는가?
         ↙ NO              YES ↘
    [Spec 이슈]           [일반화]
   동작이 명시 안 됨      모델이 일반화 못함
   → 프롬프트에 규칙 추가  → 탐지기 구축
   → 테스트 재실행        → 사람에게 라우팅
```

> **테스트는 무엇이 실패했는지 알려준다. 왜인지는 당신이 판단한다.**

### 12. 벽에 부딪혔다는 신호

| **프롬프트 과부하** | **일반화 한계** |
| --- | --- |
| 너무 많은 규칙이 서로 경쟁 | 프롬프트가 명확하고 최소한임 |
| 하나를 고치면 다른 게 깨짐 | 그런데도 모델이 못 함 |
| 모델이 혼란스러워함 | 엣지 케이스가 계속 나타남 |
| 프롬프트가 몇 페이지 길이 | 모델이 못 하는 추론이 필요 |
| **해법: 범위를 단순화하고 여러 에이전트로 분할** | **해법: 사람에게 라우팅, 한계 수용** |

> 어느 쪽이든: **탐지해야 할 일반화 오류를 찾아낸 것입니다.**

**노트 — 왼쪽 열이 멀티에이전트로 가는 진짜 이유입니다**

Lecture 7은 "뚜렷이 구별되는 페르소나가 필요할 때 MAS로 올려라"라고 했는데, 여기서 그 신호가 구체적으로 나옵니다 — **프롬프트 규칙끼리 충돌하기 시작할 때**입니다.

"멀티에이전트가 멋있어서"가 아니라 "하나의 프롬프트로 표현할 수 있는 규칙 수의 한계에 도달해서" 쪼개는 것입니다.

### 13. Phase 2 — 오류 주도 탐지 (Hamel Hussain 방법론)

고칠 수 없는 실패를 체계적으로 범주화합니다.

| 단계 | 하는 일 | 예시 |
| --- | --- | --- |
| **OPEN CODING** | 원시 실패를 수집하고 무엇이 잘못됐는지 각각 라벨링 | "사용자가 이유를 물었는데 응답 없음" |
| **AXIAL CODING** | 범주로 묶고 실패 간 공통 패턴 발견 | "EXPLANATION_REQUEST (10건)" |
| **BUILD DETECTORS** | 각 범주에 대해 프로덕션 트레이스에 패턴 매칭 | `if 'why' in message...` |
| **ROUTE** | 사람에게 / 폴백으로 / 로그로 | — |

> 각 실패 범주가 **프로덕션에서 확인할 수 있는 규칙**이 됩니다.

#### Open Coding 상세

**절차:**

1. **트레이스 30~50개를 수동으로 검토**
2. 탐색적 메모를 작성 ("저널링")
3. **첫 번째 실패에 집중** — 오류는 연쇄된다
4. 일관성을 위해 **한 명의 도메인 전문가**가 담당

**예시 메모:**
```
❌ Trace #42  "사용자가 'quick sync'라 했는데 에이전트가 60분을 잡음"
❌ Trace #67  "가용성을 확인하기 전에 초대를 보냄"
❌ Trace #89  "사용자가 '왜'라고 물었는데 에이전트가 질문을 무시함"
```

> **핵심: 아직 범주를 만들지 않는다 — 관찰만 한다.**

#### Axial Coding 상세

원시 메모를 실행 가능한 범주로 묶습니다.

```
"quick sync" → 60분
"brief chat" → 45분          →  WRONG_DURATION        13건
"short call" → 60분

캘린더 확인 전에 초대함        →  CALENDAR_ORDER         9건
초대 보낸 뒤 충돌 발견

"왜"라고 물었는데 답 없음      →  EXPLANATION_REQUEST   10건
"3시를 고른 이유가 뭔가요?"

사용자가 STOP 했는데 계속함    →  STOP_IGNORED          23건
"기다려"를 무시함
```

> **이론적 포화(Theoretical Saturation): 새 트레이스에서 새로운 실패 유형이 나오지 않을 때까지 코딩을 계속하십시오.**

**노트 — "첫 번째 실패에 집중하라"가 실무에서 중요합니다**

에이전트 트레이스는 오류가 연쇄됩니다. 3번 단계에서 잘못 판단하면 4~10번이 전부 이상해 보입니다. 그 열 개를 다 라벨링하면 **한 개의 근본 원인을 열 개의 서로 다른 문제로 착각**하게 됩니다.

**트레이스 하나당 최초 실패 지점 하나만 기록**하는 규율이 범주 통계를 신뢰할 수 있게 만듭니다.

### 14. 루브릭 점수 매기기 — 계층 구조 ⭐

> **결정론적인 것을 먼저, LLM judge는 꼭 필요할 때만.**

| 순위 | 종류 | 내용 |
| --- | --- | --- |
| **1** | **Deterministic** | **Assertion — 테스트 케이스별 검사**<br>`tool_called` · `param_contains` · `step_order`<br>빠르고, 싸고, 재현 가능 |
| **2** | **Invariants** | **범용 규칙 — 모든 출력에 적용**<br>`EMAIL_SIGNATURE` · `SMS_BREVITY` · `NO_MINIMIZERS`<br>오류 범주를 잡아냄 |
| **3** | **LLM Judge** | **미묘한 판단 — 필요할 때만**<br>"이게 도움이 되는가?" · "톤이 맥락에 맞는가?"<br>비싸고, 보정이 필요함 |

#### 코드 기반 vs 모델 기반 채점기

> **유일한 질문: 결정론적 로직을 작성할 수 있는가?**

| **Code-Based Graders** | **Model-Based Graders** |
| --- | --- |
| 문자열 매칭, 정규식, 상태 검사 | 루브릭 기반 LLM 판정, 쌍대 비교 |
| ✓ `send_email`을 호출했는가? | ? 이 응답이 도움이 되는가? |
| ✓ 본문에 `{% raw %}{{SIGNATURE}}{% endraw %}`가 있는가? | ? 톤이 맥락에 맞는가? |
| ✓ SMS가 300자 미만인가? | ? 이 설명이 명확한가? |
| ✓ 초대 전에 가용성을 확인했는가? | ? 사용자가 만족할까? |
| **빠름 · 저렴 · 재현 가능 · 디버깅 가능** | **유연 · 뉘앙스 처리 · 비쌈 · 보정 필요** |

> **경험칙: 결정론적으로 시작하고, 로직을 쓸 수 없을 때만 LLM judge를 추가하라.**

### 15. 트랜스크립트가 아니라 결과를 검사하라 ⭐

> **에이전트가 무엇을 했는지가, 무엇을 했다고 말했는지보다 중요하다.**

| ❌ 트랜스크립트 검사 | ✓ Mock 상태 검사 |
| --- | --- |
| `agent called send_email`<br>`to: ["sarah@co.com"]`<br>`subject: "Meeting"` | `# 에이전트 실행 후:`<br>`mock_calendar.events == [`<br>`  {title: "Meeting", ...} ]` |
| ✓ tool_called: pass<br>✓ param_contains: pass | ✓ 이벤트가 상태에 존재<br>✓ 참석자가 정확함 |
| **그런데 이메일이 실제로 발송됐는가?**<br>도구가 조용히 실패했을 수 있다 | **환경이 실제로 바뀌었는지 확인.**<br>주장이 아니라 실측(ground truth) |

**노트 — 이 함정은 반드시 밟습니다**

에이전트 평가를 처음 만들면 대부분 트랜스크립트를 검사합니다. 로그에 도구 호출이 보이니까 통과로 처리하는데, **도구가 예외를 삼키고 실패했어도 호출 기록은 남습니다.**

Lecture 7의 도구 설계 원칙 "결함 허용 — 정보가 담긴 오류 메시지를 반환하라"가 이것과 직결됩니다. 도구가 조용히 실패하면 에이전트도, 평가기도 속습니다.

### 16. 에이전트 시뮬레이션 환경

에이전트가 결과 없이 행동할 수 있는 샌드박스 세계입니다.

```
          [Agent]  (Claude Code, 당신의 에이전트)
             │  프롬프트 + 도구
             │  ↓ 도구 호출
    ┌────────────────────────────────────┐
    │      Simulation Environment        │
    │  Mock Calendar   events[], 가용성   │
    │  Mock Email      sent[], inbox[]    │
    │  Mock SMS        messages[]         │
    ├────────────────────────────────────┤
    │  관측 가능한 상태                    │
    │  연락처, 선호, 이력, 파일시스템        │
    │  ↳ 에이전트 실행 후 이것을 검사        │
    └────────────────────────────────────┘
             │  상태
             ↓
        [Grader]  Assertions · Invariants · LLM Judge
```

#### 왜 시뮬레이션 환경을 쓰는가

| 이유 | 내용 |
| --- | --- |
| 🔒 **안전하게 실패** | 에이전트가 이메일 100통을 보내고 회의 50개를 잡아도 **실제로는 아무 일도 안 일어남** |
| 🔄 **재현 가능** | 시행 간 상태를 리셋, 같은 시나리오를 100번 실행해 결과 비교 |
| ⚡ **빠른 반복** | 레이트 리밋 없음, 외부 서비스 API 비용 없음, 즉각 피드백 |
| 🎭 **시나리오 통제** | 엣지 케이스 주입 — 충돌하는 캘린더, 느린 API 등 |

#### 같은 환경, 다른 바깥 루프

```
        [당신의 시뮬레이션 환경]
   mock 캘린더·이메일·연락처·상태·채점기
          ↙                    ↘
  Eval Loop (Claude)      RL Loop (오픈소스)
  pass/fail → 프롬프트 수정  보상 → 역전파 → 가중치 갱신
  모델 가중치: 고정(API)    모델 가중치: 학습 가능(Llama 등)
  갱신: 사람 또는 에이전트 루프  에피소드: 수천~수백만
```

> **핵심: 결정론적 검증기가 자동화를 연다 — 에이전트가 자기 프롬프트를 스스로 최적화할 수 있다.**
> 오픈소스 모델을 쓰면 같은 시뮬레이터가 **RL 학습 환경**이 된다.

**노트 — Lecture 11과의 연결**

Lecture 11의 "Ephemeral Software 4단계 사다리"에서 4단계가 Simulation Environments였습니다. 이 강의가 그 4단계의 구체적 구현을 보여줍니다.

그리고 마지막 문장이 중요합니다 — **결정론적 검증기가 있으면 사람 없이도 개선 루프를 돌릴 수 있습니다.** Lecture 11의 "테스트가 통과할 때까지 밤새 돌린다"와 같은 이야기입니다.

### 17. 사례 연구 — 179건의 거부

두 단계 렌즈로 본 결과입니다.

| 구분 | 건수 | 내용 |
| --- | --- | --- |
| **총 거부** | **179건** | |

## Part 4: 업계는 지금 어디에 있는가 (요약)

2026년 1월, 오픈소스 자율 에이전트 프레임워크가 **2주 만에 GitHub 스타 7.8k → 153k**로 폭증한 현상을 다룹니다. 에이전트 전용 소셜 네트워크에 37,000개 에이전트가 모여 자기조직적 행동을 보였고, 동시에 **API 키 150만 개 노출, 이메일 주소 3.5만 건 유출**이 발생했습니다.

### 왜 확산됐는가

| 요소 | 내용 |
| --- | --- |
| 🏠 Local-first | 데이터가 내 것으로 남음 |
| 🧠 지속 메모리 | AI 기억상실 해결 |
| 🔌 MCP 아키텍처 | 100+ 통합 |
| 🔓 오픈소스 | 투명성을 통한 신뢰 |
| ⚡ 실제로 자율적 | 대화만 하는 게 아니라 실행함 |
| 🎰 안전보다 강력함 | **사용자가 위험을 감수함** |

### 사용자가 실제로 원하는 것

> "사람들은 '오퍼레이터'나 AI 브라우저를 원하지 않습니다. **자기 자신의 행위주체성을 반영하는 에이전트**를 원합니다. 통제권이 자기에게 있고, 에이전트가 AI 회사가 아니라 **나를 위해** 일한다고 느끼는 것."

**🎮 통제** (블랙박스가 아닌 것) · **🤝 충성** (나를 위해 일하는 것) · **🔧 커스터마이징** (내 선호)

### 개발자에게 주는 함의

| 함의 | 내용 |
| --- | --- |
| **에이전트가 사회적 존재가 된다** | 당신의 에이전트가 다른 에이전트와 상호작용한다. 대비하라 |
| **사람만이 아니라 에이전트를 위해 만들라** | 에이전트가 온라인 정보의 최대 소비자가 된다. **API-first, MCP-first** |
| **창발적 행동은 실재한다** | 프로그래밍하지 않은 일을 한다. 기능이자 버그 |
| **보안은 나중 문제가 될 수 없다** | **자격증명을 가진 에이전트 = 거대한 폭발 반경** |
| **미지의 영역이다** | AI 사회가 어떤 모습일지 아무도 모른다 |

**노트 — 이 부분은 빠르게 낡습니다**

특정 프로젝트 이름과 스타 수, 트위터 반응은 몇 달이면 의미가 바뀝니다. 다만 **마지막 표의 다섯 가지 함의**는 유효하고, 특히 "API-first, MCP-first"와 "자격증명 = 폭발 반경"은 설계 원칙으로 남습니다.

## 핵심 요약

### 강의의 논지

```
AI-native = AI가 일급 실행 계층인 시스템
        ↓
판별: 비정형 입력이 실행된 산출물이 되는가
        ↓
그러려면 명세가 "검증 가능"해야 한다 (Done When)
        ↓
그런데 에이전트는 실패한다 → 실패를 분류하라
        ↓
Spec 실패는 고치고, 일반화 실패는 탐지해서 사람에게
        ↓
결과적으로 사람은 어려운 케이스만 본다
```

### 한 문장으로 압축

| 주제 | 결론 |
| --- | --- |
| AI-native 판별 | **비정형 입력 → 실행된 산출물**로 경로가 연결되어 있는가 |
| 명세 포맷 | Context / **Done When(검증 가능)** / Requirements / Key Files |
| Done When | 검증 루프의 입력이자, **쓰는 행위 자체가 기획을 완성**시킴 |
| Key Files | 범위를 고정해 에이전트의 폭주와 중복 구현을 막음 |
| 비밀 관리 | 컨텍스트와 **트레이스 로그** 양쪽에서 막아야 함 |
| 컨텍스트 | 12주에 걸쳐 무인 정확도 20% → 95%. **컨텍스트 파일이 해자** |
| 실패 분류 | **Spec 실패(고칠 수 있음)** vs **일반화 실패(탐지·라우팅)** |
| 멀티에이전트 전환 신호 | **프롬프트 규칙끼리 충돌하기 시작할 때** |
| 오류 주도 방법론 | open coding → axial coding → 탐지기 → 라우팅 |
| Open coding 규율 | 트레이스당 **최초 실패 하나만** 기록 (오류는 연쇄됨) |
| 루브릭 계층 | **결정론적 → 불변식 → LLM judge** 순서로 |
| 채점 기준 | **결과(mock 상태)를 검사하라, 트랜스크립트가 아니라** |
| 시뮬레이션 환경 | 안전·재현·빠름·통제. 그리고 그대로 RL 환경이 됨 |
| 179건 분석 | 76건은 프롬프트로 해결, 103건은 탐지 대상 |

### 가장 중요한 네 문장

1. **"Can unstructured input become executed work product with zero human in the loop?"**
2. **모든 `Done When` 항목은 테스트 가능해야 한다.**
3. **대부분의 실패는 spec 실패다 — 그것은 고칠 수 있다.**
4. **트랜스크립트가 아니라 결과를 검사하라. 주장이 아니라 실측이다.**

## 용어 정리

| 용어 | 의미 |
| --- | --- |
| AI-Native | AI가 일급 실행 계층인 시스템 설계 (AI-assisted와 구분) |
| Spec-driven development | 검증 가능한 명세를 1차 산출물로 두는 개발 방식 |
| Done When | 명세의 검증 가능한 완료 조건 체크리스트 |
| Spec Failure | 프롬프트가 불완전해 생긴 실패 — 고칠 수 있음 |
| Generalization Failure | 모델이 새 상황으로 규칙을 확장하지 못하는 실패 — 탐지·라우팅 |
| Open Coding | 실패 트레이스를 범주 없이 관찰·기록하는 단계 |
| Axial Coding | 관찰을 실행 가능한 범주로 묶는 단계 |
| Theoretical Saturation | 새 트레이스에서 새 실패 유형이 안 나오는 지점 |
| Detector | 특정 실패 범주를 프로덕션에서 잡아내는 패턴 규칙 |
| Assertion | 테스트 케이스별 결정론적 검사 |
| Invariant | 모든 출력에 적용되는 범용 규칙 |
| Code-Based Grader | 문자열·정규식·상태 검사 기반 채점기 |
| Model-Based Grader | LLM이 루브릭으로 판정하는 채점기 |
| Simulation Environment | 부수효과 없이 에이전트를 실행·평가하는 샌드박스 |
| Ground Truth | 주장이 아니라 실제로 관측된 상태 |
